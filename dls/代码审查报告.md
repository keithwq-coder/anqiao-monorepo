## 二、总体评价

`[VERIFIED]` 这是一套**治理纪律异常严格**的 DDD 模块化单体（FastAPI + SQLAlchemy 2.0 + PostgreSQL + Alembic + Jinja2 服务端渲染），共 9,516 行 Python、6 个迁移、`368 passed / 28 skipped`（2026-08-12 记录）。安全与分层设计是真实的亮点，但存在生产部署漂移、数据模型临时补丁、大文件稀释分层三类结构性问题，以及「无代理商域」这一关键空白。

一句话：**工程质量在中小团队里属上乘，但它是「B2B 机构记录/跟进 CRM」，不是「渠道管理系统」——代理商域是全新领域，不能硬套现有模型。**

## 三、优点（应保留与复用）

1. **中央 fail-closed 策略投影层**（`policy/projection.py`，355 行）
   - 服务端字段级脱敏，`unmapped fields 默认隐藏`，无浏览器回退；三种视图级别 OWNER / COLLABORATOR / ADMINISTRATOR_EXCEPTION 在返回前即完成投影。
   - `resolve_read_access` 对非 ENABLED 用户、无授权的 MANAGER、无理由的 ADMINISTRATOR 一律 `PolicyDenied`——管理员查看敏感详情必须带审计理由（`DEC-0006` 的"审计例外"）。这是真正的"默认拒绝"。

2. **领域对象自校验**（`domain/models.py`，268 行）
   - `frozen=True, slots=True` dataclass + `__post_init__` 强制：时区感知（`_aware`）、必填 strip、互斥状态（联系人"有渠道必须 AVAILABLE"）、密码必须 Argon2id 前缀。

3. **配置期 fail-closed 禁 AI**（`config.py`）
   - `Settings.ai_enabled=True` 在配置加载即拒绝，AI 出口默认关闭。AI 能力是显式授权才开的，不是默认开。

4. **认证安全到位**（`web/auth.py` 480 行）
   - Argon2id 哈希、服务端 session（仅存 SHA-256 token hash）、CSRF 写保护、按标识符限速、持久化安全审计、禁用即失效（`session_epoch`）。

5. **幂等键**：Institution / Contact / FollowUpActivity 均带 `idempotency_key`，防重复写入。

6. **证据驱动治理**：SPEC→DECISION→TASK 门禁 + 批准哈希绑定 + 独立评审，把"AI 幻觉"当成头号流程风险来防（`AGENTS.md` 第 3 节）。

## 四、问题与风险（按严重度）

### P0 · 生产部署被依赖漂移卡死
`[VERIFIED]` `docs/NOW.md` 记录：生产 venv `fastapi 0.141.0` 要求 `starlette>=0.46`，但运行时是 `starlette 0.44.0`，`pip check` 确定性失败；而发布 payload 钉的是 `fastapi==0.136.3`。`TASK-0027` 因此在远程前置条件第 6 步 `BLOCKED`，未做任何生产变更。
**影响**：当前代码无法可靠发布；依赖版本在生产/本地/发布包三处不一致。
**建议**：冻结一处（建议以固定 release 源码生成锁文件 + wheel 哈希清单，见 TASK-0028C 提案），三处对齐后再谈发布。

### P1 · 语义字段编码进自由文本（schema-less 补丁）
`[VERIFIED]` `domain/models.py` R-029：沟通方式类别不是独立列，而是以 `【电话】` 前缀拼进 `interaction_method` 自由文本，显示时再 `split_stored_interaction_method` 拆开。注释明言"本任务无新迁移授权"。
**影响**：类别与内容耦合在同一列，无法按类别过滤/统计/校验，长期腐烂；一旦要"按沟通方式报表"就得再补迁移。
**建议**：下一轮迁移时落独立列，保留前缀兼容读旧数据。

### P1 · 分层被大文件稀释
`[VERIFIED]` 行数：`persistence/repositories.py` 1,319 行、`application/queries.py` 723 行、`web/main.py` 854 行、`persistence/models.py` 599 行。
**影响**：DDD 的模块边界在持久化层被"仓库 god-file"打破，读改一个聚合要翻千行文件，评审与 AI 导航成本高。
**建议**：按聚合拆 `repositories`（institution/contact/followup/opportunity/operation），`main.py` 拆成 page router + app factory。

### P1 · 领域模型与 ORM 双写
`[VERIFIED]` 领域 dataclass（`domain/models.py`）与 SQLAlchemy 映射（`persistence/models.py`）两套模型并行，字段需人工同步。
**影响**：字段演进时两处漂移风险（本项目已用测试钉住，但仍是结构成本）。
**建议**：若新系统从零起，可直接用 SQLAlchemy 2.0 `Mapped` + 领域方法，避免双模型；或把 dataclass 作为纯值对象、ORM 作为唯一持久化真相，明确单向映射。

### P2 · 陈旧 API 语义
`[VERIFIED]` `AccessDecision.read_only` 恒返回 `True`，注释为"S3 无写能力，S4 引入 commands"；但 `application/commands.py` 已存在。该属性语义已过时，误导读者。
**建议**：删除或改为真实反映"读投影不可写"的命名（如 `immutable_projection`）。

### P2 · 治理流程成本极高
`[VERIFIED]` `docs/tasks/active/` 30+ 个任务，大量状态是"awaiting Codex independent review"；`SPEC-BASELINE` 冻结流程要求完整基线批准才动代码。
**影响**：对"几人小公司、渠道刚起步"的迭代节奏，这套流程是显著 overhead。**对代理商系统不建议原样照搬**，应取其"SPEC→TASK 门禁"的骨架，去掉"完整基线冻结"的重门。

### P2 · UI 未验收（产品方反馈）
`[VERIFIED]` `docs/NOW.md` 记录产品方评价：dashboard 是空壳、机构页粗糙、入口不明显、"距商用产品差距大"。功能通过、可用性未过。

### P2 · 域缺失（对本次任务最关键）
`[VERIFIED]` 现有聚合只有：`Institution`（机构）、`Contact`、`FollowUpActivity`、`UserIdentity`、`RoleGrant`、`opportunity_reminders`、`operation_records`。
**没有**代理商/经销商/合伙人、区域、档位、协议、保证金、订单、回款、返利、客户报备归属、季度考核等任何渠道域实体。
**结论**：代理商管理是**全新限界上下文**，不能把代理商塞进 `Institution`（机构）里——代理商是"合作方 + 协议 + 财务 + 区域权益"的聚合，语义不同。
