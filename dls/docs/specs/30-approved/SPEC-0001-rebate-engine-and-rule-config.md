# SPEC-0001 · 规则配置域与返利引擎

- 版本：v0.1.0
- 状态：30-approved（产品方批准 2026-08-13，DEC-0012；仅批准 SPEC，未授权实现）
- 日期：2026-08-13
- 授权：无（本 SPEC 批准前不写代码）

## 背景与目标

渠道业务的档位、价盘、返利、保证金、保护期等数字是**变动的政策**（质保 12→24 个月、0730 修订、手册 v2→v3）。若写死在代码里，每次政策调整都要改代码重发。目标：把这些数字做成**管理后台可编辑的版本化配置**，代码只做通用引擎；返利计算做成**纯函数**，可离线对账。

依据：DEC-0001/0002/0003/0005/0007。

## 术语

| 词 | 定义 |
|---|---|
| 档位 | 代理商两档（区县/地级市）；经销商 3 档位（月累计价盘阶梯） |
| 返利 | 4 类（季度回款/年度达标/市场秩序/过程指标），基数=实际回款额，货款抵扣 |
| 规则快照 | 交易发生时生效的配置版本，历史对账不可变 |

## 范围

- 包含：8 张规则配置表（版本化）、返利引擎纯函数、价盘阶梯查表、区域互斥校验、返利抵扣额度模型。
- 不包含：裂变/引荐（DEC-0006 暂缓）、真实物流、真实微信支付（待商户号）、C 端零售。

## 需求（R-xxx）

- **R-001** 规则配置域提供 8 类配置表：`agent_tier`、`price_ladder`、`price_line`、`rebate_rule`、`deposit_rule`、`protection_policy`、`region_grade`、`banned_term`。
- **R-002** 每张配置表版本化：`effective_from` / `effective_to` / `version` / `status`，改规则 = 关旧版 + 插新版，**不原地改**；同一规则同一时刻至多一条 active。
- **R-003** 返利引擎为无副作用纯函数，输入含"规则快照 + 当季/年度回款 + 合规标记 + 过程指标"，输出 4 类返利明细与总额。
- **R-004** 返利基数 = 实际回款额（非开票/进货额）；总额封顶于 `rebate_cap_rate`（代理 7%、经销 4%）。
- **R-005** 价盘阶梯按月累计采购量查表，`>1600` 返回"面议"且禁止自动出价。
- **R-006** 区域互斥：同地级市内 地级市代理与区县代理互斥，DB 约束 + 应用校验双保险。
- **R-007** 返利结算计入"可用抵扣额度"，下单时冲抵应付额，微信实付 = 应付 − 抵扣。
- **R-008** 报备/订单备注字段做禁用词扫描（医疗级/诊断/治疗/医疗器械产品级）。

## 验收标准（AC-xxx）

- **AC-001** 8 张配置表可后台增改，版本化生效，历史版本不可变。
- **AC-002** 返利引擎通过 `Phase1-规则配置与返利引擎规格.md` 第 3.4 节全部金样本断言（场景 A–E + 价盘阶梯 4 例）。
- **AC-003** `>1600` 下单返回"面议"且单价为空，不产生自动价格。
- **AC-004** 同地级市重复设区县/地级市代理被拒绝（应用层 + 唯一索引双保险）。
- **AC-005** 抵扣下单：应付 100,000、可用额度 5,000 → 微信实付 95,000，抵扣流水扣减额度。
- **AC-006** 备注含"医疗级"等禁用词被拦截。

## 技术要点（DEC-0011 已锁定）

- 后端：FastAPI（JSON API，复用 crm 的 auth/policy 模式）；DB：PostgreSQL 16 + Alembic。
- 合作方端：原生微信小程序（wx.login/openid + 手机号授权绑定）。
- 公司管理后台：Jinja2 服务端渲染（与 crm ADR-0002 一致）。
- 支付：微信支付 JSAPI（统一下单/回调验签/退款原路退回）。
- 返利引擎：纯 Python 函数模块，TDD（金样本先行）。
- 版本化实现：规则查询统一走"当前 active 版本"；历史计算传"版本快照"。
