# 长护险领域术语表 · DOMAIN GLOSSARY v0.1

> 状态：基线
> 日期：2026-09-22
> 读者：产品、后端、前端、业务方（政府/医保局/商保/照护机构）
> 目的：固化领域术语，**避免「平台用户」与「业务用户」两类『用户』互相混淆**。平台术语一律走英文/代码标识，业务术语走中文正式表达，二者显式区分并在此对照。
>
> 关联：`docs/API-CONTRACT.md`（账号/组织/报告基线）、`docs/LTC-INSURANCE-SPEC.md`（流程/状态机/验收）。

> 一句话总则：**本文中所有带代码标识（等宽）的英文词均指平台对象/角色；所有中文业务词均指业务对象。凡口语说『用户』时必须指明是平台登录账号（user）还是业务申请人（Applicant）。**

---

## 1. 平台角色 vs 业务对象 总对照

| 平台标识（代码） | 平台中文 | 是否平台账号 | 业务对应 |
|---|---|---|---|
| `su` | 平台超级管理员 | 是 | 平台运维 |
| `admin` | 机构管理员 | 是 | 机构/护理院负责人 |
| `user` | 机构普通用户 | 是 | 护士/医生/护理员等员工 |
| `family_contact` | 家属联系人 | 是（非员工） | 长者家属/受托代理人 |
| `medical_insurance_staff` | 医保局经办人员 | 是 | 医保局监管人员 |
| `insurer_staff` | 长护险经办机构经办人员 | 是 | 医保经办/商保经办 |
| `assessor` | 失能评估员 | 是 | 独立评估人员 |
| — 分隔 — | — | — | — |
| **平台 `user` ≠ 业务「用户」** | | | |
| `Applicant` | 申请人/参保对象 | **否**（业务对象） | 提长护险申请的那位长者 |

> 🔴 **最重要的一条**：平台登录角色 `user`（机构员工）**不是**业务上的「用户」（长护险申请人）。业务文档/界面里说「申请用户」「参保用户」时，指的是 **Applicant 申请人**，不是 `user` 账号。二者绝不可混用。

## 2. 平台账号与角色

| 术语 | 定义 | 关键约束 |
|---|---|---|
| **Account（账号）** | 可登录平台的身份主体，绑定唯一组织主体与唯一 `role` | 账号-组织-角色一一对应 |
| **Org（机构）** | 护理院/照护服务商，`kind = nursing_home` | 多租户隔离维度 `tenant_id` |
| **vendor（厂商）** | 设备厂商/自营运营主体，`kind = vendor` | 与护理院数据严格隔离 |
| **su（超级管理员）** | 平台总管理员 | 不直接经办业务 |
| **admin（机构管理员）** | 机构内最高权限账号 | 全机构数据与配置 |
| **user（机构普通用户）** | 机构员工账号（护士/医生/护理员） | 本人经手/本机构数据 |
| **family_contact（家属联系人）** | 非员工账号，绑定一位/多位长者 | 仅绑定长者、需授权 |
| **medical_insurance_staff（医保局经办人员）** | 监管侧账号 | 统筹区只读监管 + 可暂缓 |
| **insurer_staff（经办机构经办人员）** | 长护险经办侧账号 | 待遇经办/审核/结算 |
| **assessor（失能评估员）** | 独立第三方评估账号 | 评估回避、仅评估任务 |

## 3. 业务对象（长护险核心）

| 术语 | 英文/标识 | 定义 | 关键约束 |
|---|---|---|---|
| **申请人** | `Applicant`, `applicant_id` | 提出长护险申请的参保/护理对象（通常为该长者） | 一个长者多申请（分期） |
| **长期护理保险** | LTC | 为重度失能人员提供的护理费用保障制度 | — |
| **失能等级/评估等级** | `disability_level` | 依据评估量表判定的失能程度（分档） | 仅 `SCORE_RULE` 启用且人工确认后生效 |
| **待遇** | benefit/treatment | 等级对应的护理补贴/服务/结算额度 | 由结果决定；监测证据不自动决定 |

## 4. 申请与材料

| 术语 | 标识 | 定义 |
|---|---|---|
| **长护险申请** | `Application, application_id` | 一次完整的申请流程载体 |
| **申请材料** | `Material, material_id` | 按清单模板收集的证据性材料 |
| **材料清单模板** | `material_template` | 配置化的材料项清单，`required` 标记必传 |
| **核验/受理** | materials_review | 经办核对材料齐备与有效性 |

## 5. 评估

| 术语 | 标识 | 定义 | 关键约束 |
|---|---|---|---|
| **评估任务** | `AssessmentTask, task_id` | 一次派单执行的评估单元 | 绑定评估员+冻结量表版本 |
| **评估量表** | `AssessmentScale, scale_id` | 评估计分项集合 | **版本化不可变** |
| **量表版本** | `scale_version` | 量表的不可变版本号 | 修改即新建版本 |
| **计分项** | `Item, item_id` | 量表中的单个判定条目 | 按 `domain` 分域 |
| **分域** | `domain` | 计分项归类（自理/认知/精神行为/感知沟通） | — |
| **评估员** | `assessor` | 执行现场评估的人员 | 回避校验、签名留痕 |
| **评估结果** | `AssessmentResult, result_id` | 评估的产出（分值与等级） | 需人工确认等级 |
| **派单** | assign | 从 `materials_pass` 到生成任务 | 回避 409 |

## 6. 证据（Evidence）—— 关键区分

| 术语 | 标识 | 定义 | 是否主证据 |
|---|---|---|---|
| **评估证据** | `evidence_assessment` | 评估员现场录入的量表分+佐证影像/文书 | ✅ 主证据 |
| **材料证据** | `evidence_material` | 申请人/家属提交的纸质材料影像 | 申请前置 |
| **监测证据** | `evidence_monitoring` | 安樵平台设备数据聚合（心率/呼吸/体温/在床/睡眠/离床/跌倒） | ❌ **仅辅助** |
| **结论引用链** | attached_to_conclusion | 辅助证据挂到人工结论后 | 监测证据必须挂链才可用 |

> 🔴 **监测证据红线**（重复强调）：`evidence_monitoring` **只能作为辅助证据，不能自动决定失能等级或待遇**，且必须与人工记录交叉验证并附着在人工评估结论后。

## 7. 流程节点

| 术语 | 标识/状态 | 定义 |
|---|---|---|
| **材料退回** | `materials_rejected` | 材料不符退回，申请可改后重提 |
| **待评估** | `assess_pending` | 材料齐备、等待派单 |
| **待经办审核** | `pending_review` | 结果提交后等待 `insurer_staff` 审核 |
| **退回重评** | `return` / returned | 审核不合格，重新评估 |
| **补证** | `request_more` | 要求补充证据后回到审核 |
| **暂缓** | `suspend` | 医保局对疑点流程暂停 |
| **复核/申诉** | `Review / Appeal` | 申请人对结果或待遇不满提出异议 |
| **改判** | `appeal_overruled` | 复核推翻原结果，走复评新任务 |

## 8. 易混淆词对照（防坑清单）

| 易混词 | 指代（代码/业务） | 千万别当 |
|---|---|---|
| 「用户」 | 无歧义时必须说清：`user`（平台员工账号）**或** Applicant（业务申请人） | — |
| `user` | 平台机构员工账号 | ❌ 业务「用户/参保人」 |
| Applicant（申请人） | 提申请的那位长者/参保对象 | ❌ 任何平台账号 |
| 评估员 assessor | 第三方评估账号 | ❌ 机构护士/医生 |
| 医保局经办 `medical_insurance_staff` | 监管侧账号 | ❌ 商保 `insurer_staff` |
| 经办机构 `insurer_staff` | 长护险经办机构账号 | ❌ 医保局 |
| 监测证据 monitoring | 设备数据（辅助） | ❌ 评估证据（主） |
| 评估等级 level | 量表人工判定结果 | ❌ 设备自动结论 |
| `pat`（Patient 长者） | 既有护理系统长者 | ❌ 长护险 Applicant（实务上常同一对象，但上下文不同） |

## 9. 术语变更流程

- 术语一经固化如需调整：先改本文，再改 `API-CONTRACT.md` 与 `LTC-INSURANCE-SPEC.md`，最后改代码；文档与代码不一致时**以本文为准**并立即修正代码。
