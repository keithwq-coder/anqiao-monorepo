## 1. 目标与范围

### 1.1 改造目标

把 SaaS 从「长护险单业态 + 按数据域分页签」改造为**多业态、多租户、多角色工作台**平台：

1. **四业态**：护理院 / 养老社区 / 居家养老 / 大健康。每个业态 = 一类租户模板 = 该业态完整角色栈；每个角色登录进各自不同的工作台；
2. **登录页改「业态 → 角色」两级进入**，取代现行按数据域的五页签；
3. **销售客户资产视图较完整版**：机构列表 / 设备在线 / 脱敏体征 / 告警历史 / 遥测曲线，机构主数据直读 anqiao_crm；
4. **体验演示域**：虚构机构名 + 常驻演示标识，与交付租户同构；
5. 商业目的始终是**带动硬件销售**：软件 = 硬件交付的增值载体（PRD §0.1），支持 **SaaS 租用 + 独立部署** 双形态。

### 1.2 本期非范围（业主已明确）

- CRM 反向引入 SaaS 能力：不做；
- 硬件管理员联通硬件仓库 / APP 仓库：以后做；
- 生产开号与权限分配：继续由「吴」账号经既有用户管理 API 负责（`POST /v1/admin/users`，守卫 `authPayload.username === '吴'`）。

## 3. 全系统角色 × 工作台总规格（核心交付物一）

### 3.1A 护理院角色栈工作台功能规格（全栈 · 对标竞品）

> **本节覆盖护理院业态全部角色**（业主点名 11 个 + PRD 支撑 5 个）：照护席位（公屏/护士/护工/护士长）、管理席位（院长）、职能席位（医生/人事/财务/营销/行政/IT，详规见 §3.3）、支撑席位（病案/物联运维/报表/康复/认知症）。规格以竞品调研为基准、以本司硬件为差异化；不做"核心/补充"分层——业主点名的每个角色同权重落地。

#### 3.1A.1 竞品调研摘要（2026-09-26 实测检索）

**国内机构养老/医养系统**：
- **麦麦养老**：全日制养老机构「智慧照护」方案（饮食起居/生活照料/健康护理/文娱综合服务）；
- **悦银通**：护理人员安排、护理排班、护理计划、护理登记、老人请假、护理变更、护理项目登记、**交接班**；
- **聚家养老**：老人档案全生命周期（入住评估→日常照护）+ 护理管理（计划制定→**任务派发→执行签到**→交接班记录）；
- **华录/好望达**：护工 APP（护理计划下发执行、老人生活记录、**交接班**、关爱提醒）；医养结合（医生/护士排班、照护管理、护理任务、**药品药房管理**）；
- **社村通**：护理任务直接关联护理员手机 APP，**手机扫码、拍照清单式完成照护计划**；护士 APP/PC 确认**医嘱执行时间**；
- **龙邦**：医生/药师/护士/健康师工作子模块 + 「护理好帮手」App（护理项目执行、医生巡诊登记）；
- **智慧病房案例（荣科等）**：护士站护理交互大屏、床旁屏、生命体征自动监测（已获二类医疗器械注册）。

**制度与国标**：《养老机构等级划分与评定》实施指南要求 24 小时值班 + **电子交接班记录表**（时间、人员、特殊老人诊断、基本生命体征、异常情况、处理方法及结果），按楼层建立交接班制度。

**国际长照 EHR（PointClickCare，北美 LTC 约 60% 份额等）**：**eMAR** 电子给药记录（扫码给药、减少差错）、**ADL flow sheet** 点护记录（床旁实时 charting）、**care plan** 图表化与多学科团队（IDT）工作流、**shift report/handoff** 交接班工具、MDS 评估；2026 选型榜单将 eMAR/MDS/care plan/ADL/shift handoff 列为长照软件核心能力。

**行业共识闭环**：能力评估 → 照护计划 → 任务下发 → 执行留痕 → 跟踪预警 → 交接班归档。

**③ 管床护工（`nursing_caregiver` → nursing_staff）**

**④ 护士长（`nursing_head` → care_desk）**

### 3.3 护理院新增六角色工作台设计（v0.2 提案，业主授权起草，待确认后实施）

> 起草原则：① 全部按 PRD §3.2 **独立账号类**规范（一人一号、一个权限 = 一个工作台，杜绝横向兼任）；② **复用既有数据面**（遥测/告警/报表/床位），新建的只是「岗位视角的组装」（§12.4 左侧 SOP 流程树 + 右侧工作间），不新建数据采集链路；③ 每个角色尽量挂接硬件数据，避免沦为 PRD §0.2 禁止的「纯文字录入 SaaS」；④ 六个工作台共用一套**职能工作台骨架组件**（SOP 树 + 内容区），各自挂不同数据面板——DRY 且符合分类学。
> **以下为提案，业主逐条确认/删改后才进入实现与 API-CONTRACT 登记。**

**① 医生（院内医务）`facility_doctor` → facility_doctor_studio**
- 看什么：管床长者健康档案（复用病案数据面）、守护仪连续体征基线（心率/呼吸/睡眠分期）、告警历史；
- 办什么：查房记录、医嘱与健康干预登记——**写入必须挂接硬件体征证据包**（PRD §0.2 硬件证据优先）；
- 硬件关系：体征遥测只读 + 告警处置协同（复用既有告警状态流）；
- 边界：算法/硬件不替代医生定级（PRD 硬件结论中立原则，`conclusion` 恒 null）。

**② 人事 `facility_hr` → facility_hr_studio**
- 看什么：员工花名册、排班表（复用既有班次数据 `getShiftInfo`）、照护采集仪打卡留痕；
- 办什么：排班编排、员工档案维护、考勤核对；
- 硬件关系：ACA-01 照护采集仪（智能照护工牌）在岗打卡数据——该硬件为按单排产（PRD §1.1），**无打卡数据时空态诚实呈现**；
- 边界：不接触长者医疗数据（权限隔离）。

**③ 财务（院侧）`facility_finance` → facility_finance_studio**
- 看什么：床位/护理费账册、长护险申报汇总（复用院长工作台的申报归档数据面）、结算报表（复用 `reports_center` 数据面）；
- 办什么：月度对账、长护险申报的财务确认、应收台账导出；
- 硬件关系：结算凭证挂接物联证据（连续在床凭证汇编、翻身合规报告——报表中心已有能力），审核时可对撞核验。

**④ 营销（入住营销）`facility_marketing` → facility_marketing_studio**
- 看什么：实住率/空床态势（本机构真实数据）、服务能力概览；
- 办什么：入住咨询登记、意向客户跟进台账（院内最小实现，**不动 CRM、不做 CRM 反向引入**）；
- 硬件关系：向意向家属演示守护仪/雷达能力（与体验域同构的演示逻辑）。

**⑤ 行政 `facility_admin` → facility_admin_studio**
- 看什么：行政事务台账、设备离线/故障清单（复用 `device_monitoring` 数据面）；
- 办什么：行政事务登记与跟进、设备报修流转（与院内物联运维协同）；
- 硬件关系：设备异常 → 报修联动（设备状态只读 + 报修记录）。

**⑥ IT `facility_it` → facility_it_studio**
- 看什么：设备在线率与离线漏斗的**网络/终端归因视图**、本机构账号席位情况；
- 办什么：网络与终端问题登记、向平台方（中科安樵）提交支持请求；
- 硬件关系：网络状态 → 设备在线的关联呈现（离线原因分类）；
- 边界（须写清，防与既有角色混杂）：`device_monitoring`（院内物联运维专员，PRD 已有）管**感知硬件本体**（巡检/标定/OTA）；`facility_it` 管**网络、终端与账号支撑**。两者数据面同源、职责分层。

**六角色共性实现约定**（确认后随 P0 落地）：
1. 逐角色在 `auth.js` 增加 `ROLE_WORKSPACE_MAP`/`ROLE_DATA_SCOPE_MAP`/`ROLE_PERMISSIONS` 条目（scope 均为 `org`），`seed.js` ACCOUNTS 增演示席位，API-CONTRACT 契约先行；
2. 六个工作台 = 1 个骨架组件 + 6 份岗位配置（SOP 树节点 + 面板挂载清单），TDD 覆盖权限越权 403；
3. P0 只实现**业主确认保留的角色**——业主可删改本节任何条目，未确认的角色不渲染（登录页角色卡同理）。

## 4. 租户模型与「租用/独立部署」双形态配置规范（核心交付物二）

### 4.1 租户模型扩展（最小改动）

现有 `TENANT_CONFIGS` 即租户注册表，**不新建租户子系统**，仅扩展：

```js
// seed.js TENANT_CONFIGS 条目扩展（示意，实施以契约为准）
cust_org01: {
  name: '康宁护理院（演示）',        // 虚构名，常驻演示标识
  kind: 'nursing_home',
  vertical: 'nursing_home',         // 新增：业态标识 nursing_home | senior_community | home_care | health_wellness
  template: 'nursing_home_v1',      // 新增：业态租户模板版本
  deployment: 'saas',               // 新增：saas | standalone
}
```

- **业态租户模板** = 该业态的角色栈 + 工作台配置 + `buildTenant` 数据分支选择（机构照护型带 occupiedBeds；运营/监管型走空数据分支）；
- **开租户流程**：「吴」在用户管理（`/v1/admin/users`，既有守卫不变）选业态模板 → 系统按模板生成租户注册 + 该业态角色栈的账号席位 → 再按客户情况逐席开号。**API 契约先登记 `API-CONTRACT.md`（N 编号），后实现（SDD 纪律）**。

### 4.2 双形态配置规范

| 维度 | SaaS 租用 | 独立部署 |
|---|---|---|
| 部署形态 | 共享 anqiao-saas 实例（现状，Node 20 + MySQL 双模式） | 客户环境独立实例 + 独立数据库，同一套代码与租户模板 |
| 数据隔离 | 租户内 `tenant_id` 行级隔离（现状机制沿用；一账号一组织，`/v1/auth/switch` 仅本组织） | 物理隔离（独立库），规格与 SaaS 相同 |
| 设备归属 | `device_registry` + 「设备 ↔ 体验角色群」N:M 分配（PRD §2.3.2 已实现） | 客户购置/租用设备随实例本地登记 |
| 许可/计费 | **待业主定义**（§9 问题 5） | **待业主定义**（§9 问题 5） |
| 升级路径 | 平台统一升级 | 版本发布包 + 升级工具（随 P3 期细化） |

> 数据隔离等级与许可机制属商务决策，技术上两条路线均可支撑；在业主给出要求前，本设计不做技术选型倾斜。

### 9.1 问题 5 平实说明（SaaS 租用 vs 独立部署）

用大白话讲，这个问题只关乎一件事：**卖给客户的软件装在哪、怎么收钱。**

- **SaaS 租用（方案 A，现在已经是这个形态）**：客户不开装任何东西，拿我们发的账号密码，打开浏览器登录**部署在我们服务器上**的系统。我们统一升级、统一维护。适合大多数民营护理院、居家养老服务中心——省心、按年付费。
- **独立部署（方案 B，现在还没做）**：当客户（尤其政府背景单位或大型集团）提出**"我的数据不能放在你们的服务器上"**时，我们把整套系统原样安装到**客户自己的服务器**上，数据和网络都封闭在客户单位内。通常一次性买断 + 每年收维护费。
- **现在要不要决定？不用。** P0（护理院打样）、P1、P2 全部在方案 A 上进行，**完全不受影响**；方案 B 只是"多一种交付方式"。建议：**等第一个真客户提出数据落地方案要求时再拍板**，届时我们拿客户的具体要求出一页纸选型对比，业主勾选即可。
- 技术上两条路线本设计都已预留（租户模型 `deployment` 字段），不存在"现在不定以后返工"的风险。
