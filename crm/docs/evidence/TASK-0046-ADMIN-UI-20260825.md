## Design decisions

1. **No new backend endpoints**: every mutating control posts to the
   existing `/api/admin/*` endpoints with the reason fields the API
   requires; the pages are read-only rendering + fetch-driven forms
   (TASK-0043 pattern).
2. **Template consolidation**: three separate templates (admin_users /
   admin_transfer / admin_erase) — the card allows consolidation, but three
   pages keep each form family small and testable; recorded here per card
   instruction.
3. **User list is enabled-only** ([VERIFIED] `UserRepository.find_all_active`
   returns only `status == 'enabled'` users; there is no all-users query and
   no user-list API): the /admin user table lists enabled users only, so
   the 启用 (enable) control has no target row after a disable. The disable
   flow works (row disappears after refresh); re-enabling a disabled user
   has no UI entry because the backend does not expose disabled users to any
   list surface. **Not worked around** (hard boundary: no backend change);
   recorded here as a backend capability boundary. Enable API remains
   available at `POST /api/admin/users/{id}/enable`.
4. **Role options are exactly the three live roles** (administrator /
   manager / business_user) — `general_manager` (removed by DEC-0172) is
   never offered; the API itself rejects it (400) as the test verifies.
5. **Self-action excluded in UI** and enforced by the API (R-015): the
   admin's own row shows 当前账号 and no mutating forms.
