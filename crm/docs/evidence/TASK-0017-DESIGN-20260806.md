## 2. Erasure record structure

### New table: `erasure_records`

| Column | Type | Constraints | Purpose |
|---|---|---|---|
| `id` | UUID PK | NOT NULL | Surrogate key |
| `target_type` | String(80) | NOT NULL | "institution" or "contact" |
| `target_id` | UUID | NOT NULL | The erased record's ID (kept; not personal data) |
| `erased_by_user_id` | UUID FK→user_identities | NOT NULL, ondelete RESTRICT | Operator (R-004) |
| `erasure_reason` | Text | NOT NULL, `char_length(btrim(reason)) > 0` | Why (R-002/R-004) |
| `erasure_scope` | Text | NOT NULL | What was deleted (field names, not values) |
| `erased_at` | timestamptz | NOT NULL | When (R-004) |
| `propagate_by` | timestamptz | NOT NULL, `propagate_by > erased_at` | Deadline: erased_at + 30 days (DEC-0104) |
| `propagation_status` | String(24) | NOT NULL, CHECK IN ('pending','verified','incomplete') | R-005 marking |
| `propagation_verified_at` | timestamptz | nullable | When propagation was verified |
| `is_request_fulfillment` | Boolean | NOT NULL, default false | R-008: marks当事人删除请求满足 |
| `request_reference` | Text | nullable | Optional reference to the deletion request (no personal content) |

### CHECK constraints

- `erasure_reason` non-blank (`char_length(btrim(erasure_reason)) > 0`)
- `propagate_by > erased_at` (window is positive)
- `propagation_status IN ('pending','verified','incomplete')`
- `propagation_verified_at IS NULL OR propagation_status <> 'pending'`
  (verified_at only set when status is not pending)

### Audit payload (R-004: no personal values)

The audit event (`audit_events`) for an erasure carries:
- `action`: `"institution.erasure"` or `"contact.erasure"`
- `target_type`: `"institution"` or `"contact"`
- `target_id`: the record ID
- `reason`: the erasure reason
- `before_state`: `{"name_present": true, "contact_count": 3, ...}` — field
  presence flags and counts, NEVER field values
- `after_state`: `{"erased": true, "propagate_by": "2026-09-05T..."}` — status
  and deadline, NEVER personal content

## 4. Erasure semantics

### What "permanent erasure" does to an institution record

SPEC-0011 R-003: erasure is independent of archive. The institution row is NOT
deleted (FK constraints with RESTRICT prevent this cleanly). Instead, personal
data fields are irreversibly blanked:

- `name` → set to `"[已删除]"` (non-blank to satisfy `name_not_blank` CHECK)
- `source_description` → set to `"[已删除]"`
- `source_kind` → set to `null`
- `category` → set to `null`
- `region` → set to `null`
- `source_evidence_reference` → set to `null`
- All contacts under the institution: personal fields blanked
  (`name`, `phone`, `email`, `wechat`, `other_channel`, `channel_notes` → null;
  `role_label` → `"[已删除]"` to satisfy `identity_present` CHECK)

This is irreversible in the application: the original values are gone from the
live database. The audit and erasure_records rows retain only field-presence
flags, never values.

### Confirmation requirement (§8)

The route requires `confirm=true` in the request body. Without it, the route
returns 400. This is the explicit administrator confirmation per SPEC §8
("执行前必须由管理员明确确认").

### Audit write failure (§8)

"删除审计写入失败时，删除操作不得显示为成功。" The erasure, erasure_records
row, and audit event are in one `transaction_session` — if any fails, the
entire transaction rolls back and the route returns an error.

## 5. Backup propagation semantics (DEC-0104)

### 30-day window

`propagate_by = erased_at + 30 days`. Backups taken before `propagate_by` may
still contain the erased data. After `propagate_by`, backups older than the
erasure time are treated as purged (superseded by newer backups without the
data).

### Synthetic pg_dump rehearsal

`scripts/synthetic_backup_rehearsal.py` (local only, touches nothing remote):
1. Creates a synthetic SQLite database with test data containing a "PHONE_LEAK_MARKER"
2. Takes a "backup" (serializes the DB to a file)
3. Erases a record via the erasure command
4. Takes a second "backup"
5. Verifies the erased personal values are absent from the second backup
6. Marks the erasure record's `propagation_status` as 'verified' or 'incomplete'

This is a synthetic rehearsal, not a production backup. It proves the
documented recovery path and propagation semantics.
