## 2. R2 defect analysis (scope-key fix)

### Problem

`resolve_read_access` (`projection.py:177-186`) grants a scoped `MANAGER` the
`COLLABORATOR` view only when:

```python
Role.MANAGER in subject.roles
and record.management_scope_key is not None
and record.management_scope_key in subject.management_scope_keys
```

`QueryService` builds `RecordSnapshot` in three methods
(`find_institutions`, `get_institution_detail`, `get_contacts`,
`get_activity_summaries`) without ever setting `management_scope_key`. It
defaults to `None`, so the MANAGER branch always falls through to
`PolicyDenied`. This is fail-closed (no leak) but means a scoped manager sees
zero records — the management surface cannot function.

### Fix [INFERENCE — engineering wiring, not a new business rule]

Set `management_scope_key=institution.region` on every `RecordSnapshot`
constructed in `QueryService`.

Authority and reasoning:
- SPEC-0002 R-020: "其他管理层只能查看其明确授权管理范围内的同类精简信息；
  没有明确管理范围时默认不返回业务数据。" A manager's authorized scope is
  their `scope_reference` (loaded into `management_scope_keys` by
  `RoleGrantRepository`). The record's scope is its `region` — the only
  institution field that represents a geographic/business scope.
- DEC-0013: "其他管理层查看获授权范围." The scope_reference IS the authorized
  scope; region is the record's scope dimension.
- TASK-0007 design note (line 66): "manager grants contribute their
  `scope_reference` as scope keys" — the subject side is established; the record
  side was left un-wired (TASK-0007 line 76 explicitly excluded institution
  route population).
- No new field, column, or migration is introduced. Both `institution.region`
  and `RoleGrantModel.scope_reference` are existing free-text `String` columns.
- When `institution.region` is `None`, `management_scope_key` is `None`, and the
  MANAGER branch denies — exactly R-020's "没有明确管理范围时默认不返回业务数据."
- `GENERAL_MANAGER` is unaffected: its branch (`projection.py:170-175`) does not
  check `management_scope_key` at all (company-wide scope per R-019).

### Scope of change

`src/crm/application/queries.py`: add `management_scope_key=institution.region`
to every `RecordSnapshot(...)` call. This is within the task card's owned paths.

## 3. Capability-area to SPEC-rule mapping

### Area A: Audited role grant/revoke (R-005, R-015, AC-003)

| SPEC rule | Requirement | Implementation |
|---|---|---|
| R-005 | Grant/revoke must record operator, target, time, reason, before/after state | `GrantRoleCommand` / `RevokeRoleCommand` write `role_grants` row + `audit_events` row with `before_state`/`after_state` JSON in one transaction |
| R-015 | User cannot elevate own role or delete audit | Route checks `actor_user_id != target_user_id`; audit deletion is never offered |
| AC-003 | Admin manages users: enable/disable/grant/revoke audited with operator, target, reason, time, before/after | Audit event carries all fields |
| R-006 | Least privilege; default deny | Only `ADMINISTRATOR` role may call grant/revoke routes |
| R-003 | New identity cannot read business data until enabled + role assigned | Grant command does not enable the user; enable is a separate action |

**Idempotency (R-012 analog for grants)**: granting an already-active identical
role (same user, same role, same scope_reference) is a no-op success — it does
not create a duplicate grant row or a second audit event. Revoking an
already-revoked grant is a no-op success. This matches R-012's "已成功项重试时
不产生重复历史" principle applied to grants.

**Manager scope requirement**: `RoleGrantModel` has a CHECK constraint
`role <> 'manager' OR scope_reference IS NOT NULL`. The grant command enforces
this at the domain level before persistence (`RoleGrant.__post_init__` already
validates it).

### Area B: User enable/disable (R-004, R-005, R-014, AC-003, AC-004)

| SPEC rule | Requirement | Implementation |
|---|---|---|
| R-004 | User has pending/enabled/disabled; disabled immediately rejects new access; history not deleted | `EnableUserCommand` / `DisableUserCommand` set `user_identities.status`; `bump_session_epoch` invalidates existing sessions |
| R-005 | Enable/disable must record operator, target, time, reason, before/after | Audit event with `before_state`/`after_state` JSON |
| R-014 | Revoked/disabled sessions must expire within a verifiable short bound | `bump_session_epoch` increments `session_epoch`; `validate_session` already checks epoch mismatch and invalidates (DEC-0044, verified in `auth.py`) |
| AC-004 | Disabled account cannot access; history/audit/ownership not deleted | Disable only sets status + bumps epoch; no row deletion |

**R-011 prompt**: SPEC R-011 says "停用仍持有记录的用户前，系统必须提示未完成
的责任归属." The disable route will check for institutions owned by the target
user and return them as a prompt. The admin may then proceed (the disable is not
blocked — R-004 says "停用后立即拒绝新访问") but the prompt is recorded in the
audit `failure_summary` or `reason` field. Batch transfer (Area D) is the path
to reassign those records before or after disable.

**Self-disable prohibition (R-015)**: an administrator cannot disable their own
account. The route checks `actor_user_id != target_user_id`.

### Area C: Single ownership transfer (R-009, R-010, AC-005, AC-006)

| SPEC rule | Requirement | Implementation |
|---|---|---|
| R-009 | Transfer must specify new owner, transferor, time, reason; old owner, new owner, and history not overwritten | `TransferOwnershipCommand` writes `institution_owner_history` row (append-only) + updates `institutions.owner_user_id` + audit event, all in one transaction |
| R-010 | New owner gains permissions; old owner loses owner-specific permissions | `owner_user_id` update is the single source of truth; policy projection reads it |
| AC-005 | Admin transfers A→B: B gains owner perms, A loses, history preserved | `institution_owner_history` row records previous_owner, new_owner, transferred_by, reason, effective_at |
| AC-006 | New owner invalid/disabled → transfer fails, original owner unchanged | Command validates new owner exists and is `ENABLED` with a business role before writing |

**Administrator-only**: transfer is an administrator operation per DEC-0013
("Customer reassignment remains an administrator operation unless a later
approved SPEC explicitly changes it").

**Idempotency**: re-transferring the same institution to the same current owner
(no-op transfer) is a no-op success — it does not create a duplicate history
row. This matches R-012's idempotency principle.

### Area D: Batch ownership transfer (R-011, R-012, AC-007)

| SPEC rule | Requirement | Implementation |
|---|---|---|
| R-011 | Admin can batch transfer; each record retains traceable result; responsibility never silently empty | `BatchTransferOwnershipCommand` iterates institutions, applying Area C logic per record |
| R-012 | Partial failure: success/failure recorded per item; no duplicate transfer of already-successful items | Each item returns `{institution_id, success, error}`; successful items commit individually; failed items are recorded with `failure_summary` |
| AC-007 | Batch with invalid items: success/failure per item; retry of successful items does not duplicate history | Idempotency check per item: if current owner already equals new owner, skip as success |

**Transaction strategy**: per-item transactions (not one big transaction). R-012
requires "成功和失败项分别记录" — a single transaction would roll back all on
any failure, which contradicts "不得把整批显示为全部成功" but also contradicts
partial success. Per-item transactions allow partial success with per-item audit
records. The batch result is a list of per-item outcomes.

### Area E: Read-only management summaries (R-019, R-020, R-021, R-022, R-023, AC-013, AC-014, AC-015, AC-016, AC-017)

| SPEC rule | Requirement | Implementation |
|---|---|---|
| R-019 | GM views company-wide concise summaries; no raw contact/source/original text | `ManagementSummaryQuery` returns counts and concise_progress only, using the collaborator projection (masked) |
| R-020 | Other management: only authorized scope; no scope → no data | Scoped MANAGER sees only records where `management_scope_key` (region) is in their `management_scope_keys` |
| R-021 | Management is read-only: no modify, transfer, account management, or grant | Route is GET-only; no write commands exposed |
| R-023 | Aggregation must not reveal restricted info via small-sample inference | Summary returns counts ≥ a minimum threshold or suppresses breakdown; concise_progress only (no raw text) |
| AC-013 | GM: company-wide summaries, no sensitive original | Collaborator projection enforced |
| AC-014 | Other management: authorized scope only, scope-out invisible | Policy projection denies scope-out records |
| AC-015 | Management cannot modify/transfer/manage accounts by role alone | GET-only route, no write dependencies |

**Summary content**: institution count, active count, archived count, latest
follow-up date (from concise_progress), has-next-action count. All derived from
the collaborator projection — no raw contact values, no factual_body, no
source_description. The summary is computed per-record through the existing
`project_record` policy, then aggregated.

**Small-sample protection (R-023/AC-017)**: if a summary group has fewer than 3
records, the breakdown is suppressed (only the total count is shown) to prevent
inferring individual records. This is the minimal R-023 implementation.
