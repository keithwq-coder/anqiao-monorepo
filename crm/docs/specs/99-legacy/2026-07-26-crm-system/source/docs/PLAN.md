# Plan: 中科安樵 CRM 系统 v1.0
_Locked via Grill-Me（Act 1 完成）→ 交由 Superpowers 五阶段框架执行_

---

## 一、目标（Goal）

构建专业级 B2B CRM 系统。核心性能定义：**AI 抓取与分析能力足够强大**（非高并发、非响应速度）。

MVP 三大核心模块：

1. **商机采集中心** — 7 渠道爬虫 + 智能去重评分 + 飞书日报推送
2. **客户智能管理** — 艾森豪威尔矩阵评级 + 防撞单机制 + 分级跟进提醒
3. **销售漏斗 BI 分析** — 11 阶段转化率监控 + 销售预测

## 二、已锁定的关键决策

| # | 决策点 | 最终选择 | 理由 |
|---|--------|---------|------|
| 1 | 架构路线 | 独立专业 CRM 系统（非飞书原生） | 完全定制爬虫/评分，支撑百万级数据，预留 SaaS 化 |
| 2 | 飞书定位 | 第二存储 + 知识中台（异步同步，非实时） | 数据沉淀构建知识飞轮，Phase 2 接 RAG/LLM |
| 3 | 前端 | React 18 + TypeScript + Ant Design Pro | 现成组件最多（500+），AI 生成质量最高，不造轮子 |
| 4 | 后端 | FastAPI (Python 3.11) + SQLAlchemy | AI 业务逻辑生成能力最强，数据处理生态最优 |
| 5 | 数据库 | PostgreSQL 16 + TimescaleDB | 时序分区支撑 BI 分析 |
| 6 | 分析引擎 | DuckDB（批量分析）+ Redis（缓存） | 列式计算比 Pandas 快百倍，满足"分析能力强大" |
| 7 | 爬虫 | Scrapy（静态站）+ Playwright（JS 渲染站） | 7 渠道混合覆盖 |
| 8 | 任务调度 | Celery + Redis（作为 broker） | 定时爬取 + 分级提醒任务 |
| 9 | 部署 | **跳过 Docker**，原生安装到腾讯云轻量服务器 | 性能无容器损耗，调试直接，运维简单 |
| 10 | 进程守护 | Supervisor（自动重启 + 日志管理） | 可靠性优先：故障 15 分钟内自愈 |
| 11 | 客户评级 | 艾森豪威尔矩阵：A(重要紧急/每天)、B(紧急不重要/每周)、C(重要不紧急/每月)、D(不重要不紧急·潜在/季度)，支持手动调整 | 已确认 |
| 12 | 销售流程 | 11 阶段标准漏斗 + 双重防撞单（录入查重 + 需求分析阶段锁定归属） | 对标行业最佳实践 |
| 13 | 开发模式 | AI-only 开发，无工期约束，零历史资产 | 已确认 |
| 14 | 可靠性定义 | 数据零丢失、爬虫稳定、自动恢复 > 并发/响应速度 | 已确认 |

## 三、AI 工具链选型与跨平台协同工作流

### 3.1 工具分工矩阵（人机协同核心）

| 角色 | 工具（模型） | 负责任务域 | 选型理由 |
|------|-------------|-----------|---------|
| **总架构师 / 协调者** | Qoder（Qwen-3.5-max-preview） | 架构设计、任务拆解、跨模块集成、最终裁决 | 推理与工程上下文能力最强，作为"主脑" |
| **前端工程师** | Kimi CLI（kimi-k3） | React 页面、AntD Pro 组件、图表 UI | 长上下文利于消化组件库文档，UI 细节好 |
| **后端 / 数据工程师** | ZCode（GLM-5.1） | FastAPI 接口、SQL Schema、DuckDB 分析、评分算法 | GLM 系列 SQL/Python 数据处理强 |
| **爬虫工程师** | OpenCode（Grok / GLM-5.1） | Scrapy/Playwright 脚本、反爬对抗、代理池 | Grok 对实时网络信息与反爬理解好 |
| **交叉审查员** | Qoder ⇄ ZCode 互评 | 每个任务完成后的 Code Review | 双模型交叉验证，规避单模型幻觉 |
| **产品负责人（人类）** | 您 | 需求裁决、阶段验收、生产部署确认 | 唯一决策 Gate |

### 3.2 跨平台协同规则（避免上下文丢失）

1. **单一事实源**：所有工具共享 `docs/` 目录下的文档（PLAN.md、ARCHITECTURE.md、API_SPEC.yaml、TASKS.md），每个 AI 开工前必须先读文档，完工后必须更新文档。
2. **任务交接协议**：每个任务完成后在 `docs/TASKS.md` 中登记：`任务编号 | 执行工具 | 输入文件 | 输出文件 | 验收状态`。下一个工具从这里接力，不依赖对话记忆。
3. **Git 分支纪律**：每个任务一个分支（`task/3.2.1-crawler-core`），完成 → 交叉审查 → 合并 main。禁止多任务混在一个分支。
4. **人类介入点（Gate）**：
   - Gate 1：Phase 2 设计文档验收（您确认 Schema/API/页面结构）
   - Gate 2：每个 Sprint 结束的功能演示验收
   - Gate 3：生产部署前的最终确认（执行 `_deploy.py` 前）
5. **失败升级路径**：任一工具连续 2 次未通过交叉审查 → 升级给 Qoder 仲裁 → 仍无法解决 → 升级给人类。

### 3.3 小任务原则（规避大任务）

- **硬性规则：每个任务 ≤ 2~4 小时 AI 工作量，单次改动 ≤ 500 行代码，涉及文件 ≤ 5 个。**
- 每个任务必须有：明确输入、明确输出、可验证的验收标准。
- 任何"实现整个模块"级别的需求必须先拆解为任务清单再执行。

## 五、风险与缓解

| 级别 | 风险 | 缓解措施 | 责任工具 |
|------|------|---------|---------|
| 🔴 | 7 渠道反爬策略变更导致爬虫失效 | 代理 IP 池 + 指纹伪装 + 渠道级降级告警 + 人工补录通道 | OpenCode |
| 🔴 | 撞单误判（企业名称模糊匹配） | 相似度阈值分档：高置信自动判、边界项进人工复核队列 | ZCode |
| 🔴 | 单机部署单点故障 | Supervisor 自动重启 + 每日备份（本地 + 飞书 Base 双份）+ 磁盘/CPU 告警 | Qoder |
| 🟡 | 飞书 API 限流 | 批量调用 + 指数退避重试 + 6 小时异步同步（非实时） | Qoder |
| 🟡 | 多 AI 工具上下文交接丢失 | `docs/TASKS.md` 交接协议 + 文档单一事实源 | 人类监督 |
| 🟡 | 服务器资源不足（爬虫高峰） | 建议配置 8 核 16G；Celery 并发数可配置限流 | — |

## 七、验收标准（Definition of Done）

MVP 上线须全部满足：
1. ✅ 7 渠道爬虫连续运行 7 天无人工干预，日均新增商机 ≥ 目标量
2. ✅ 去重准确率 ≥ 95%，撞单误报率 ≤ 2%
3. ✅ A/B/C/D 分级提醒按日/周/月/季度准时触发，飞书通知送达
4. ✅ BI 看板 10 万行数据查询 ≤ 3 秒
5. ✅ 模拟故障（杀进程/断网）后 15 分钟内自动恢复
6. ✅ 每日备份成功写入飞书 Base
7. ✅ 销售团队试用 1 周，关键流程可独立完成
