## 1. Problem

内部 B2B/G CRM 会由多人共同使用。系统必须明确“谁正在操作、谁负责哪条
业务记录、谁能看到什么、人员变化后如何安全转交”，否则脱敏、审计、AI
最小上下文和后续商机协作都无法可靠执行。

本 SPEC 只定义与业务行为有关的身份和权限合同，不预先指定飞书、密码、
单点登录或其他技术方案。

## 3. Goal and success measure

每次读取、修改、转交和例外访问都能回答：操作者是谁、依据什么权限、作用于
哪条记录、结果是什么；人员停用后不能继续访问，但其历史工作和审计记录不会
丢失或被改成其他人的行为。

非技术人员可以这样判断成功：用不同身份查看同一机构，看到的内容符合分工；
停用一个账号后该账号立即不能进入系统；把客户转交给新负责人后，新旧负责人
和转交原因都能追溯。

## 4. Non-goals

本版本不定义：

- 飞书 OAuth、密码、短信、硬件密钥或其他具体登录技术；
- 中科安樵真实人员名单、部门组织架构或生产账号导入；
- 面向客户、合作伙伴或公众的外部门户账号；
- 经销商结算、佣金、绩效或销售提成权限；
- 绕过 `SPEC-0001` 脱敏矩阵的“内部全员可见”；
- 生产环境的密码策略、身份供应商采购或账号费用。

## 5. Users and permissions

### 已确定身份概念

- **业务人员**：内部获准使用 CRM 的人员。可以处理本人负责的记录；对其他
  记录只能获得后续 SPEC 明确允许的脱敏、精简信息。
- **记录负责人**：某一机构、联系人关系、线索、商机或任务当前的责任归属。
  这是记录关系，不是永久账号角色；同一业务人员可以负责多条记录。
- **管理员**：管理账号、角色、停用、必要转交和审计。管理员不能把“管理
  系统”解释为日常无理由查看全部客户敏感详情；完整详情访问继续遵守
  `SPEC-0001` 的例外访问与审计规则。
- **未授权主体**：未登录、账号无效、已停用或未获相应业务权限的主体。不能
  读取业务内容。
- **总经理**：可查看全公司范围的汇总、精简业务进度、工作分配和待处理事项；
  默认只读，不自动查看完整联系方式、客户原话、原始跟进正文或证据。
- **其他管理层**：只可查看明确授权管理范围内的同类汇总和精简信息；默认
  只读，不因职务名称自动扩展范围或获得敏感原文。

## 6. Required behavior

- R-001: 每个可登录人员必须有稳定且唯一的内部用户身份；显示姓名、手机号、
  邮箱或飞书标识变化时，不产生另一个历史操作者。
- R-002: 不允许多人共享同一个业务身份。所有写入、查看敏感详情和管理操作
  必须归因到具体内部身份。
- R-003: 新身份默认不能读取业务数据；只有明确启用并分配获批角色/范围后才
  获得相应权限。
- R-004: 用户身份至少有 `待启用`、`启用`、`停用` 状态。停用后立即拒绝新
  访问，但不删除其历史记录、负责人历史和审计归因。
- R-005: 角色授予、撤销、用户启用和停用必须记录操作者、对象、时间、原因、
  变更前后状态。
- R-006: 权限按最小必要原则计算；没有明确允许的行为默认拒绝，没有明确
  显示规则的字段默认隐藏。
- R-007: 记录负责人只能获得处理本人负责记录所必需的权限，不因“负责人”
  身份获得其他记录或系统管理权限。
- R-008: 管理员可以管理账号和授权，但日常业务详情仍受 `SPEC-0001` 例外
  访问理由与审计约束。
- R-009: 负责人转交必须指定新负责人、转交人、时间和原因；旧负责人、新
  负责人及转交历史不可被无痕覆盖。
- R-010: 单条转交完成后，新负责人取得后续工作权限，旧负责人失去负责人
  专属权限；旧负责人是否仍能看到脱敏摘要由普通业务人员规则决定。
- R-011: 停用仍持有记录的用户前，系统必须提示未完成的责任归属；管理员可以
  分批或批量转交，但每条记录保留可追溯结果。不能把责任静默设为空。
- R-012: 批量转交部分失败时，成功和失败项分别记录，不得把整批显示为全部
  成功，也不得重复转交已经成功的项目。
- R-013: 页面、搜索、导出、API、AI 上下文和后台任务使用同一身份、角色、
  归属和字段可见规则，不得存在替代路径绕过权限。
- R-014: 权限被撤销或账号被停用后，已有会话必须在可验证的短时边界内失效；
  精确技术时限由实现架构确定并测试，不得保持无限期访问。
- R-015: 用户不能提高自己的角色、修改自己的访问范围或删除权限审计。
- R-016: 管理员不能通过修改历史操作者或负责人历史来掩盖原操作归属。
- R-017: 身份提供方不可用时，系统不得伪造登录成功；已有会话是否继续仅按
  已批准且可验证的安全策略执行。
- R-018: 后续 SPEC 可以在本权限模型上增加更窄的操作权限，但不能静默扩大
  `SPEC-0001` 已批准的敏感字段可见范围。

- R-019: 总经理可查看全公司范围的管理汇总、精简进度、工作分配和待处理
  事项，但默认不能查看完整联系方式、原始跟进正文、客户原话或证据。
- R-020: 其他管理层只能查看其明确授权管理范围内的同类汇总和精简信息；
  没有明确管理范围时默认不返回业务数据。
- R-021: 管理层查看权限默认只读，不包含修改记录、转交客户、管理账号、
  授予权限或删除审计的能力。
- R-022: 管理层确需查看敏感详情时，必须使用与管理员例外访问同等或更严格
  的说明原因和审计流程；管理层职务本身不能自动放开敏感字段。
- R-023: 管理层汇总只能由当前用户有权查看的精简信息计算，不得通过汇总、
  计数、筛选或下钻反推出受限个人信息或原始业务内容。

## 7. Data and integrations

### 最小业务合同

| 对象 | 必需信息 | 系统维护信息 |
|---|---|---|
| 用户身份 | 显示名称、账号状态 | 稳定身份、创建/更新时间、身份提供方关联（如有） |
| 角色授权 | 用户、角色、适用范围 | 授权人、授权时间、撤销人/时间、原因 |
| 负责人关系 | 业务记录、当前负责人 | 生效时间、转交人、前负责人、新负责人、原因 |
| 权限审计 | 操作者、动作、目标、结果 | 时间、原因、前后状态、失败信息的非敏感摘要 |

具体登录提供方是可替换集成。无论使用本地身份、飞书或其他企业身份源，都
必须映射到同一个稳定内部身份，不能把外部显示名直接当作不可变主键。

审计信息不得包含密码、令牌、验证码或完整秘密。用户身份停用不删除历史
审计。生产留存期限由数据生命周期 SPEC 决定。

## 8. Failure and edge behavior

- 未知、停用、无角色或越权身份访问时，拒绝请求且不泄露目标记录是否存在。
- 角色或范围配置冲突时，采用更小权限并提示管理员处理，不自动放大权限。
- 转交的新负责人无效、已停用或无业务角色时，转交失败且原负责人不变。
- 批量停用/转交的部分失败必须逐项可重试，不能伪装成全部成功。
- 身份源返回重复或不一致标识时停止自动绑定，进入管理员核对，不合并历史。
- 审计写入失败时，高风险管理操作不得显示成功；读取普通业务记录也不得
  因审计组件异常回退为完整数据。

## 9. Acceptance criteria

- AC-001: Given 一个新建但未授权的身份，when 请求任何业务记录，then 拒绝
  且不返回业务内容。
- AC-002: Given 一个启用的业务人员，when 查看本人负责记录和他人记录，
  then 分别应用负责人必要详情和普通业务人员脱敏摘要。
- AC-003: Given 管理员管理用户，when 启用、停用、授予或撤销角色，then
  操作者、对象、原因、时间和前后状态均可审计。
- AC-004: Given 一个账号被停用，when 再次访问，then 访问被拒绝且其历史
  跟进、审计和责任归属不被删除或改名。
- AC-005: Given 一条有效转交，when 管理员将记录从 A 转给 B，then B 获得
  负责人权限、A 失去负责人专属权限，并保留转交人、原因和完整归属历史。
- AC-006: Given 新负责人无效或停用，when 尝试转交，then 操作失败且原归属
  保持不变。
- AC-007: Given 批量转交存在部分无效项，when 执行，then 成功/失败逐项明确，
  已成功项重试时不产生重复历史。
- AC-008: Given 同一用户的外部显示信息变化，when 重新登录，then 历史仍
  归属于同一个稳定内部身份。
- AC-009: Given 页面、搜索、导出、API、AI 上下文和后台任务，when 同一
  身份访问同一记录，then 权限和字段可见结果一致。
- AC-010: Given 管理员没有填写例外访问原因，when 请求完整业务详情，then
  请求被拒绝；填写真实原因后访问被审计。
- AC-011: Given 用户尝试提高自身权限或修改审计历史，when 请求提交，then
  拒绝且产生安全审计。
- AC-012: Given 身份提供方不可用，when 新登录发生，then 不显示登录成功且
  不创建虚假身份。

- AC-013: Given 总经理打开管理视图，when 查看全公司业务，then 只获得
  全公司范围的汇总、精简进度、分配和待处理信息，不返回默认受限的敏感原文。
- AC-014: Given 其他管理层打开管理视图，when 查看业务，then 只返回其
  获授权管理范围内的同类精简信息，范围外记录和汇总不可见。
- AC-015: Given 任一管理层用户，when 尝试修改或转交记录、管理账号或授予
  权限，then 仅凭管理层查看角色不能执行该操作。
- AC-016: Given 管理层确需敏感详情，when 未填写例外访问原因，then 拒绝；
  按例外流程访问时记录人员、目标、时间和原因。
- AC-017: Given 管理汇总包含小样本或筛选组合，when 结果可能暴露受限个人
  信息或原始内容，then 隐藏或降低明细程度而不是泄露。

自动化权限矩阵检查、生产身份提供方验证和人工业务验收必须分开记录。

## 10. Constraints and safety

- 继续执行 `SPEC-0001` 的最小必要展示、字段默认隐藏和例外访问审计。
- 不在文档、日志或测试数据中存放密码、令牌、验证码或真实员工隐私。
- 真实账号、生产通讯录和身份提供方连接在单独授权前不得使用。
- 权限拒绝、停用和转交必须可重复验证；不能仅依赖页面隐藏按钮。
- 技术登录方案由后续架构根据批准的业务合同选择，不要求产品负责人选择
  JWT、Session、OAuth 等工程术语。

## 11. Open decisions

### OD-001: 管理层查看角色

- **Status**: RESOLVED by `DEC-0013`.
- **Decision**: 设置总经理和其他管理层查看角色。总经理查看全公司精简管理
  信息；其他管理层查看获授权范围。管理层默认只读，不获得转交、修改、账号
  管理或无理由查看敏感原文的权限。

登录技术、会话机制和身份提供方属于后续架构决策，只要满足本 SPEC 行为，
不要求产品负责人选择。
