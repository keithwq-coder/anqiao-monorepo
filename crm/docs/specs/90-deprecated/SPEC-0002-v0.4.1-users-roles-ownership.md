## 0. 版本说明（本草案对 0.3.0 的变更）

0.3.0 的增量是「新增 agent 登录角色 + 用户手机号字段」。本草案按 `DEC-0149`
做三处变更；v0.4.1（`DEC-0172`，2026-08-24）在此基础上**删除
general_manager 角色**：

1. **废弃 agent 登录角色**：删除 R-024 与角色枚举中的 `agent`；登录用户回到
   三种内部角色。「代理」回归为客户类型（渠道子例，见 SPEC-0001 v0.8.0）。
2. **admin 权限重定义**：全局完整可见 + 无理由修改业务记录（自动留痕），移除
   0.2.0/0.3.0 中「管理员日常业务详情须例外访问理由」的约束（原 R-008）。
3. **v0.4.1 删除 general_manager（gm）**：原 gm 能力归并——点名分配与进池
   仅属 administrator；全公司脱敏摘要由 administrator 查看，其他管理层
   （manager）只能查看授权范围（scope）内的脱敏摘要。产品负责人 2026-08-24
   指令：「过去的『总经理』等角色全部删除，今天新设定的才是正确的」。

用户手机号字段（R-025）保留，其余规则沿用 0.3.0 除非下文明确覆盖。

## 1. Problem

内部 B2B/G CRM 会由多人共同使用。系统必须明确"谁正在操作、谁负责哪条业务
记录、谁能看到什么、人员变化后如何安全转交"，否则脱敏、审计、AI 最小上下文
和后续商机协作都无法可靠执行。

本 SPEC 只定义与业务行为有关的身份和权限合同，不预先指定飞书、密码、单点
登录或其他技术方案。

## 3. Goal and success measure

每次读取、修改、转交和例外访问都能回答：操作者是谁、依据什么权限、作用于哪
条记录、结果是什么；人员停用后不能继续访问，但其历史工作和审计记录不会丢失
或被改成其他人的行为。

非技术人员判断成功：用不同身份查看同一客户，看到的内容符合分工；停用一个
账号后该账号立即不能进入系统；把客户转交或进池后，归属与原因都能追溯；admin
能看到全公司视图，其他管理层只能看授权范围，但不能改客户内容；业务人员能认领公池。

## 4. Non-goals

本版本不定义：

- 飞书 OAuth、密码、短信、硬件密钥或其他具体登录技术；
- 中科安樵真实人员名单、部门组织架构或生产账号导入；
- 面向客户或公众的外部门户账号（「代理」已不再是登录角色，而是客户类型）；
- 经销商结算、佣金、绩效或销售提成权限；
- 绕过 `SPEC-0001` 脱敏矩阵的"内部全员可见"；
- 生产环境的密码策略、身份供应商采购或账号费用。

## 5. Users and permissions

- **业务人员（business_user）**：内部获准使用 CRM 的人员。名下客户完整可见
  可写；他人客户脱敏 + 精简进度；可认领公池客户（见 SPEC-0001）。
- **记录负责人**：某一客户、联系人关系、线索、商机或任务当前的责任归属。是
  记录关系，不是永久角色。
- **管理员（administrator）**：全局完整可见 + 无理由修改任何业务记录（自动
  留痕：谁、何时、改哪条）+ 账号/角色/停用管理 + 点名分配 + 进池 + 归档。
- **其他管理层（manager）**：授权范围内脱敏只读（必须带 scope）；不因职务名称
  自动扩大范围。
- **未授权主体**：未登录、账号无效、已停用或无角色者，不能读取业务内容。

（v0.4.1：原「总经理（general_manager）」角色已删除，`DEC-0172`；其点名分配/
进池能力归并至 administrator。）

## 6. Required behavior

### 保留规则（0.3.0，术语按「客户」）

- R-001: 每个可登录人员必须有稳定且唯一的内部用户身份；显示名、手机号、邮箱
  或飞书标识变化时，不产生另一个历史操作者。
- R-002: 不允许多人共享同一个业务身份。所有写入、查看敏感详情和管理操作必须
  归因到具体内部身份。
- R-003: 新身份默认不能读取业务数据；只有明确启用并分配获批角色/范围后才获得
  相应权限。
- R-004: 用户身份至少有 `待启用`、`启用`、`停用` 状态。停用后立即拒绝新访问，
  但不删除其历史记录、负责人历史和审计归因。
- R-005: 角色授予、撤销、用户启用和停用必须记录操作者、对象、时间、原因、
  变更前后状态。
- R-006: 权限按最小必要原则计算；没有明确允许的行为默认拒绝，没有明确显示
  规则的字段默认隐藏。
- R-007: 记录负责人只能获得处理本人负责记录所必需的权限，不因"负责人"身份
  获得其他记录或系统管理权限。
- R-008（**v0.4.0 修改**）: 管理员可以管理账号和授权，并且**全局完整可见**、
  可**无理由修改任何业务记录**（自动留痕：谁、何时、改了哪条；理由可填可不
  填）。审计底线（R-016 不可掩盖原归属、R-005 留痕）保留。此条覆盖 0.3.0 中
  「管理员日常业务详情须例外访问理由」的约束。
- R-009: 负责人转交必须指定新负责人、转交人、时间和原因；旧负责人、新负责人
  及转交历史不可被无痕覆盖。
- R-010: 单条转交完成后，新负责人取得后续工作权限，旧负责人失去负责人专属
  权限；旧负责人是否仍能看到脱敏摘要由普通业务人员规则决定。
- R-011: 停用仍持有记录的用户前，系统必须提示未完成的责任归属；管理员可以
  分批或批量转交，但每条记录保留可追溯结果。不能把责任静默设为空（进池另见
  R-027）。
- R-012: 批量转交部分失败时，成功和失败项分别记录，不得把整批显示为全部成功，
  也不得重复转交已经成功的项目。
- R-013: 页面、搜索、导出、API、AI 上下文和后台任务使用同一身份、角色、归属
  和字段可见规则，不得存在替代路径绕过权限。
- R-014: 权限被撤销或账号被停用后，已有会话必须在可验证的短时边界内失效；精确
  技术时限由实现架构确定并测试，不得保持无限期访问。
- R-015: 用户不能提高自己的角色、修改自己的访问范围或删除权限审计。
- R-016: 管理员不能通过修改历史操作者或负责人历史来掩盖原操作归属。
- R-017: 身份提供方不可用时，系统不得伪造登录成功；已有会话是否继续仅按已批准
  且可验证的安全策略执行。
- R-018: 后续 SPEC 可以在本权限模型上增加更窄的操作权限，但不能静默扩大
  `SPEC-0001` 已批准的敏感字段可见范围。
- R-019: administrator 可查看全公司范围的管理汇总、精简进度、工作分配和待处理
  事项；其他管理层只能查看授权范围（scope）内的同类信息。均默认不能查看完整
  联系方式、原始跟进正文、客户原话或证据（脱敏只读）。
- R-020: 其他管理层只能查看其明确授权管理范围内的同类汇总和精简信息；没有明确
  管理范围时默认不返回业务数据。
- R-021（**v0.4.1 修改**）: 管理层查看默认只读；点名分配与进池两个写动作
  **仅属 administrator**（见 R-026 / R-027）。manager 为纯只读，不拥有修改客户
  内容、管理账号、授予权限或删除审计的能力。
- R-022: 管理层确需查看敏感详情时，必须使用与管理员例外访问同等或更严格的说明
  原因和审计流程；管理层职务本身不能自动放开敏感字段。
- R-023: 管理层汇总只能由当前用户有权查看的精简信息计算，不得通过汇总、计数、
  筛选或下钻反推出受限个人信息或原始业务内容。
- R-024: **已删除**（v0.4.0 废弃 agent 登录角色）。
- R-025: 用户身份可记录一个手机号字段。该字段可选、非唯一、不用于登录认证；
  仅作身份资料，并在管理员可见范围内展示。手机号为空或缺失不影响账号启用、
  登录或任何角色权限。

### 新增规则（DEC-0149）

- R-026: **点名分配**：admin 把客户直接转交给某个具体业务人员。admin 的
  分配理由可选（自动留痕）。分配写负责人历史并留审计。
- R-027: **进池**：admin 手动把客户转为无主（在池）状态，写负责人历史 +
  必填原因（见 SPEC-0001 v0.8.0 公池）。认领权仅属 business_user。

## 7. Data and integrations

### 最小业务合同

| 对象 | 必需信息 | 系统维护信息 |
|---|---|---|
| 用户身份 | 显示名称、账号状态 | 稳定身份、创建/更新时间、身份提供方关联（如有）、手机号（可选，非唯一，不用于登录） |
| 角色授权 | 用户、角色、适用范围 | 授权人、授权时间、撤销人/时间、原因 |
| 负责人关系 | 业务记录、当前负责人 | 生效时间、转交人/进池人、前负责人、新负责人、原因、是否进池 |
| 权限审计 | 操作者、动作、目标、结果 | 时间、原因、前后状态、失败信息的非敏感摘要 |

具体登录提供方是可替换集成。无论使用本地身份、飞书或其他企业身份源，都必须
映射到同一个稳定内部身份，不能把外部显示名直接当作不可变主键。

审计信息不得包含密码、令牌、验证码或完整秘密。用户身份停用不删除历史审计。
生产留存期限由数据生命周期 SPEC 决定。

## 8. Failure and edge behavior

- 未知、停用、无角色或越权身份访问时，拒绝请求且不泄露目标记录是否存在。
- 角色或范围配置冲突时，采用更小权限并提示管理员处理，不自动放大权限。
- 转交的新负责人无效、已停用或无业务角色时，转交失败且原负责人不变。
- 批量停用/转交的部分失败必须逐项可重试，不能伪装成全部成功。
- 身份源返回重复或不一致标识时停止自动绑定，进入管理员核对，不合并历史。
- 审计写入失败时，高风险管理操作不得显示成功；读取普通业务记录也不得因审计
  组件异常回退为完整数据。
- admin 点名分配可不填理由但自动留痕。
- 手机号字段为空、重复或格式不规范时，按"可选且不用于登录"处理：不阻断账号
  启用与登录；如管理员录入的手机号格式非法，仅在录入界面提示。

## 9. Acceptance criteria

0.3.0 的 AC-001…AC-017 保留（删除 AC-018…AC-021 中 agent 相关项；AC-020 手机号
保留）。新增：

- AC-022: Given 一个被授予 `agent` 角色的账号（旧模型产物），when 尝试登录，
  then 该角色不再属于合法登录角色集合（系统按无角色/停用处理）；如账号仍
  enabled 且被保留，需单独治理决定其去留。
- AC-023: Given admin 修改一条非本人负责的业务记录，when 执行且不填理由，then
  修改成功且审计记录（谁、何时、改哪条）自动生成。
- AC-024: Given administrator 查看全公司客户（脱敏摘要），when 展示，then
  全部脱敏（无渠道值/原文/原话），且任何修改/进池以外写动作对 manager 被拒绝。
- AC-025: Given administrator 点名分配客户，when 执行，then 转交成功并留负责人
  历史与审计（理由可选，自动留痕）。
- AC-026: Given admin 把客户进池，when 执行，then owner 置空、在池状态
  置位、负责人历史与原因可追溯。

自动化权限矩阵检查、生产身份提供方验证和人工业务验收必须分开记录。

## 10. Constraints and safety

- 继续执行 `SPEC-0001` 的最小必要展示、字段默认隐藏和例外访问审计（admin 全局
  完整可见由 R-008 覆盖）。
- 不在文档、日志或测试数据中存放密码、令牌、验证码或真实员工隐私。
- 真实账号、生产通讯录和身份提供方连接在单独授权前不得使用。
- 权限拒绝、停用和转交必须可重复验证；不能仅依赖页面隐藏按钮。
- 技术登录方案由后续架构根据批准的业务合同选择，不要求产品负责人选择 JWT、
  Session、OAuth 等工程术语。
- 废弃的 `agent` 登录角色及其已存在账号（如 zxx）是旧模型产物，其停用/删除/
  迁移回退需单独生产授权（见 `DEC-0149`/`DEC-0150`）。

## 11. Open decisions

- **OD-001（agent 角色历史产物清理）**: 生产上已存在的 `agent` 角色定义、
  `zxx` 账号与迁移 0007 如何处置（停用/删除/回退），需单独生产授权；本 SPEC
  只定义"agent 不再是合法登录角色"，不授权清理动作。
- **OD-002（admin 点名分配理由下拉项）**: admin 分配理由的"可下拉选"具体选项清单
  未定；建议第一版提供（转岗、离职、区域调整、其他）等通用项，待产品负责人
  确认。
- **OD-003（manager 的 scope 来源）**: manager 的授权范围（scope）如何定义与
  维护未定（按区域/按客户类型/按自定义分组）；本版本保留"必须带 scope"，
  具体来源待确认。
