# SPEC-0014: 账号用户名与密码自助修改

- Spec ID: SPEC-0014
- Version: 0.2.0
- Status: APPROVED
- Product owner: User
- Prepared by: Codex (PI)
- Last updated: 2026-08-13
- Supersedes: 0.1.0 (deprecated `90-deprecated/SPEC-0014-v0.1.0-account-credentials-modification.md`)

## 1. Problem

`SPEC-0002` 定义了身份、角色、归属与停用/转交，但未定义已启用业务
人员修改本人登录凭据（用户名、密码）的行为。当前系统只能在数据库层
直接改密/改名，没有受控的应用层入口，也没有审计。

产品负责人要求：允许业务人员自助修改本人的用户名和密码，但以 `sa`、
`dl` 开头的用户名属于受保护前缀，不允许通过该入口修改用户名（防止
误改销售/代理渠道的命名约定）。密码可改。

本 SPEC 只定义凭据修改的最小行为合同，不定义身份供应商、SSO、密码
强度策略或生产账号开通流程（仍由 `SPEC-0002` 非目标项管束）。

本版本（v0.2.0）对齐 `SPEC-0002 v0.3.0`（`DEC-0144`）新增的「代理」
角色：`agent` 角色与业务人员同等享自助修改本人凭据的能力。

## 2. Verified context

- [VERIFIED] `SPEC-0002 v0.2.0` R-004 定义了 `待启用/启用/停用` 三态；
  R-005 要求角色授予/撤销、启用/停用必须留痕；R-008 管理员可管理账号。
- [VERIFIED] `SPEC-0002` 非目标项明确排除"生产环境的密码策略、身份
  供应商采购或账号费用"——本 SPEC 不引入密码强度策略，只定义"修改"
  这个动作的最小合同。
- [VERIFIED] 现有代码 `src/crm/persistence/user_repository.py` 仅有
  `find_*`、`create`、`disable_user`、`bump_session_epoch`，无任何
  `update_username` / `change_password` 方法；路由层 `src/crm/web/routes/auth.py`
  仅有 `login`/`logout`/`session`，无修改凭据入口。
- [VERIFIED] 密码以 argon2id 存储（`$argon2id$v=19$m=65536,t=3,p=4$...`），
  校验使用 `argon2.PasswordHasher().verify()`；`hash_password()` 在
  `src/crm/web/auth.py`。
- [VERIFIED] `SPEC-0002` R-014：权限被撤销或账号停用后，已有会话必须在
  可验证短时边界内失效。改密后必须同等失效旧会话。
- [VERIFIED] `SPEC-0002` 审计约束：审计信息不得包含密码、令牌、验证码
  或完整秘密。
- [VERIFIED] 产品负责人 2026-08-05 明确要求：允许修改用户名和密码，但
  `sa`/`dl` 两个前缀的用户名不可修改。
- [VERIFIED] `DEC-0144`（2026-08-13）决定新增「代理」角色，且
  `SPEC-0002 v0.3.0` R-024 规定代理与业务人员享有同等的自助凭据修改能力；
  因此本 v0.2.0 将操作主体从 `business_user`/`administrator` 扩展为
  `business_user`/`administrator`/`agent`。
- [UNKNOWN] 是否需要管理员代改他人凭据的能力——本 SPEC 不定义。
- [UNKNOWN] 是否需要"修改用户名后旧用户名冷却期"等防滥用规则——本 SPEC
  不定义。

## 3. Goal and success measure

已启用的业务人员（含代理）可通过应用内入口修改本人登录用户名和密码；
修改成功后旧会话失效、必须用新凭据重新登录；修改行为留痕（不含密码明文）。
`sa`、`dl` 前缀的用户名被系统拒绝修改（仅密码可改）。

非技术人员可以这样判断成功：用 `wq` 登录后能在页面上改自己的密码，
改完用新密码重新登录成功；尝试把 `sa1` 改成别的名字时系统拒绝并提示
该前缀受保护；代理账号同样能自助改密。

## 4. Non-goals

本版本不定义：

- 管理员代改他人用户名/密码（只支持本人改本人）；
- 密码强度策略、过期强制改密、历史密码不复用规则（仍由 `SPEC-0002`
  非目标项管束，未来需要单独 SPEC）；
- 身份供应商、SSO、飞书 OAuth 集成（`SPEC-0002` 非目标）；
- 用户名修改后的冷却期、修改频率限制；
- 受保护前缀列表的运行时管理界面（前缀列表是 SPEC 级常量，不是运行时
  配置）；
- 忘记密码的自助重置流程（需要独立的身份验证通道，本 SPEC 不涉及）；
- `display_name`（显示名）的修改——`SPEC-0002` R-001 已说明显示名变化
  不产生新历史操作者，但修改入口不在本 SPEC 范围。

## 5. Users and permissions

- **操作主体**：仅限 `status = enabled` 且角色含 `business_user`、
  `administrator` 或 `agent` 的本人。管理员不能通过本入口改他人凭据。
- **作用对象**：仅限操作者本人的 `user_identities` 行。
- **前置校验**：修改密码前必须验证当前密码正确；修改用户名前必须验证
  当前密码正确（用户名修改是高风险操作，需二次确认身份）。
- **前缀保护**：当目标用户名的当前值以 `sa` 或 `dl` 开头（大小写
  不敏感，按 `lower(username)` 判断）时，用户名修改请求被拒绝，返回
  明确的"该用户名前缀受保护，不可修改"提示。密码修改不受此规则影响。
- **状态保护**：`pending`/`disabled` 状态的账号不能使用本入口；未登录
  身份不能访问。

## 6. Required behavior

- R-001: 修改密码必须先通过 `verify_password(current_password,
  stored_hash)` 校验当前密码；校验失败拒绝且不透露目标记录是否存在。
- R-002: 新密码经 `hash_password()` 生成 argon2id 哈希后写入
  `user_identities.password_hash`；明文密码不落日志、不落审计、不进
  会话。
- R-003: 修改用户名必须先校验当前密码（同 R-001）。
- R-004: 若当前用户名（`lower(username)`）以 `sa` 或 `dl` 开头，用户名
  修改请求被拒绝；密码修改不受影响。
- R-005: 新用户名必须满足 `SPEC-0002` 既有约束（唯一、非空、长度上限
  64）；与现有其他用户名冲突时拒绝，不自动追加后缀。
- R-006: 用户名或密码修改成功后，立即调用 `bump_session_epoch(user_id)`
  使该用户所有已有会话失效（对齐 `SPEC-0002` R-014）；操作者本人需用
  新凭据重新登录。
- R-007: 每次成功的用户名/密码修改必须写 `audit_events`，记录操作者、
  目标用户、动作类型（`user.username_change` / `user.password_change`）、
  时间、结果；审计内容**不含**新旧密码、**不含**新用户名明文。
- R-008: 审计写入失败时，凭据修改不得显示成功（对齐 `SPEC-0002` 高风险
  管理操作约束）。
- R-009: 页面和 API 使用同一身份与校验规则，不得存在绕过前缀保护或
  二次确认的替代路径（对齐 `SPEC-0002` R-013）。
- R-010: CSRF 保护同其他写操作（`DEC-0044`）；表单提交需带 CSRF token。
- R-011: `agent` 角色与 `business_user` 享有相同的自助凭据修改权限
  （对齐 `SPEC-0002 v0.3.0` R-024）。

## 7. Data and integrations

### 受影响表

- `user_identities`：更新 `username` 和/或 `password_hash`、`updated_at`。
- `audit_events`：插入一条审计记录。
- `server_sessions`：通过 `bump_session_epoch` 使旧会话失效（已有方法）。

### 受保护前缀常量

受保护用户名前缀列表为 SPEC 级常量：`["sa", "dl"]`。实现以
`lower(username).startswith(prefix)` 判断。该列表不是运行时配置，变更
需修订本 SPEC。

### 不变的数据关系

- 修改用户名不改变 `user_identities.id`（稳定内部身份，对齐
  `SPEC-0002` R-001）。
- 修改用户名/密码不改变 `role_grants`、`institutions.owner_user_id`、
  `follow_up_activities.recorded_by_user_id` 等任何归属关系——这些按
  `id` 引用，与 `username` 无关。

## 8. Failure and edge behavior

- 当前密码错误：拒绝，不透露账号是否存在，不写审计（避免信息泄露）。
- 新用户名与现有用户名冲突：拒绝，提示已被占用，不修改。
- 当前用户名受前缀保护但尝试改用户名：拒绝，提示前缀受保护。
- 账号在操作过程中被管理员停用：写入前再次校验 `status = enabled`，
  失败则拒绝。
- 审计写入失败：凭据修改回滚，不显示成功。
- 新密码与旧密码相同：允许（本 SPEC 不引入密码历史策略），但提示"新
  密码与当前密码相同"。
- 用户名为空或超长：按 `SPEC-0002` 既有约束拒绝。

## 9. Acceptance criteria

- AC-001: Given 已启用的业务人员 `wq`，when 提交正确当前密码与新密码，
  then 密码更新成功、旧会话失效、用新密码可登录、审计记录写入。
- AC-002: Given 已启用的业务人员 `wq`，when 提交错误当前密码，then 拒绝
  且不写审计、不泄露账号信息。
- AC-003: Given 已启用的业务人员 `sa1`，when 尝试修改用户名为 `sa1new`，
  then 拒绝并提示"该用户名前缀受保护，不可修改"。
- AC-004: Given 已启用的业务人员 `wq`（前缀不在保护列表），when 提交
  正确当前密码与新用户名 `wq2`，then 用户名更新成功、旧会话失效、用
  `wq2` 可登录、`id` 不变、归属关系不变。
- AC-005: Given 已启用的业务人员，when 新用户名与另一现有用户名冲突，
  then 拒绝并提示已被占用，不修改。
- AC-006: Given 未登录或 `disabled`/`pending` 状态的账号，when 访问修改
  凭据入口，then 拒绝。
- AC-007: Given `sa1` 修改密码（用户名不改），when 当前密码正确，then
  密码修改成功（前缀保护只限制用户名，不限制密码）。
- AC-008: Given 审计写入失败，when 凭据修改已执行，then 事务回滚、不
  显示成功。
- AC-009: Given API 与页面两条路径，when 同一用户修改凭据，then 前缀
  保护、二次确认、会话失效行为一致。
- AC-010: Given 密码修改成功，when 旧会话尝试访问受保护资源，then
  会话已被失效、拒绝访问。
- AC-011: Given 一个已启用的 `agent` 账号，when 自助修改本人密码，then
  成功、旧会话失效、用新密码可登录、审计记录写入（与业务人员一致）。

## 10. Safety limitations

- 本 SPEC 不授权真实业务数据的外部传输、外部模型调用或部署。
- 本 SPEC 不引入密码强度策略；如未来需要，必须单独 SPEC。
- 受保护前缀列表变更必须修订本 SPEC，不得通过运行时配置绕过。
- 本 SPEC 不授权管理员代改他人凭据；如未来需要，必须单独 SPEC 定义
  审计与授权边界。
- 实施仍需 `AGENTS.md` §5 全部 gate：本 SPEC 批准 + active task +
  产品负责人明确授权。

## 11. Open decisions

- OD-001: 是否需要"修改用户名后 N 天内不可再改"的冷却期？当前默认
  不需要，待产品负责人确认。
- OD-002: 受保护前缀是否需要扩展到 `admin` 前缀？当前 `admin` 用户名
  是管理员账号，其修改属管理员账号管理范畴，不在本 SPEC 定义。
- OD-003: 是否需要管理员代改他人密码的能力？当前默认不需要，待产品
  负责人确认。
