## 0. 版本说明（本草案对 0.7.0 的变更）

0.7.0 已批准的核心结构（记录/联系人/跟进/脱敏/更正审计/AI 跟进教练）不变。
本版本做三处增量：

1. **术语统一**：主记录术语由「机构/企业」改为「客户」（对齐 `CONTEXT.md`
   领域词汇表；「机构/企业」是旧/过窄叫法）。对应新「客户类型」字段，「直接
   采购」类型大致对应旧「机构/企业」记录。
2. **新增「客户类型」字段**：三值纯标签（直接采购 / 个人 / 渠道），见 §6。
3. **新增「公池」（无主状态）**：客户可处于无负责人状态，见 §6。

除上述明确覆盖外，0.7.0 的 R-001…R-036、AC-001…AC-029 与字段级脱敏矩阵继续
生效，术语按「客户」理解。

## 1. Problem

在引入商机采集、AI 评分、销售漏斗、提醒或报表之前，系统需要先建立一套最小
且可信的业务事实：团队正在跟进什么，以及围绕它实际发生过什么。

本文件定义获批的业务对象、用户角色、字段、权限、客户分类、公池归属和跟进
规则。SPEC 批准不等于实施授权，当前仍不能修改应用代码。

## 3. Goal and success measure

有权限的使用者可以建立一条可持续跟进的客户记录（带客户类型），在有联系对象
时补充联系人，追加跟进活动，并重新打开时看到完整、顺序一致的历史。无负责人
的客户进入公池，对业务角色脱敏可见并可被认领。销售人员编辑跟进时能获得 AI
质量建议；AI 建议与事实输入分离，仅确认后的内容进入业务记录。

非技术人员判断成功：选定一条真实业务关系，录入（含类型）后补充一次实际沟通
或行动，再次查看时信息不丢失、不串对象、不被无痕改写；把客户放进公池后别的
业务人员能脱敏看到并认领；认领后归属清晰可追溯。

## 4. Non-goals

本版本不包含：

- 自动爬取或导入外部线索（外部线索属于 SPEC-0003 商机发现）；
- AI/MEDDIC 商机评分、自动分级、赢单概率或自主业务决策；本 SPEC 的 AI 范围仅
  限于跟进记录质量教练（商机 AI 见 SPEC-0003）；
- 销售漏斗阶段、预测或 BI 看板；
- 自动提醒、飞书同步、消息推送或其他外部写入；
- 批量迁移历史数据；
- 生产部署、计费、多租户或 SaaS 化；
- `个人` 类型的建档/跟进/商机流程与个人隐私（PII）——第一版仅预留类型值；
- `渠道` 类型的层级结构与佣金/结算（non-goal）；
- 公池防囤积护栏（第一版不设）。

## 5. Users and permissions

- [VERIFIED] 登录角色由 `SPEC-0002` 定义：`administrator` / `manager` /
  `business_user`（`agent`、`general_manager` 登录角色已废弃删除）。
- **记录负责人**：名下客户完整可见可写；维护本人负责客户的当前信息、追加跟进、
  按 R-031 更正/撤回。
- **其他业务人员**：他人客户仅脱敏 + 精简进度；可认领公池客户（见 §6）。
- **管理员（admin）**：全局完整可见 + 无理由修改业务记录（自动留痕）+ 归档 +
  点名分配 + 进池（见 `SPEC-0002` v0.4.1）。
- **其他管理层（manager）**：授权范围内脱敏只读（需 scope）。
- **未授权主体**：不能读取任何业务内容。

## 6. Required behavior

0.7.0 的 R-001…R-036 由 `DEC-0010` 批准，本版本保留并沿用（术语「机构/企业」
按「客户」理解）。以下为保留规则摘要与新增规则。

### 保留规则（0.7.0，术语更新）

- R-001: 有权限的使用者可以通过手工输入建立一条客户记录。
- R-002: 每条记录使用稳定且不依赖名称的唯一身份，名称变更不产生另一条记录。
- R-003: 有权限的使用者可以在客户记录下建立并查看联系人；联系人不是独立记录。
- R-004: 使用者可以查看客户及其联系人的当前获批信息。
- R-005: 使用者可以为客户记录追加跟进活动；每次活动至少保留发生时间、沟通
  方式、记录时间、记录者和事实正文。
- R-006: 再次打开记录时，系统按确定顺序展示已保存的跟进历史。
- R-007: 对记录或历史的修改不能无痕覆盖；更正、撤销和删除规则见 R-031。
- R-008: 本版本的核心流程不依赖外部数据源、AI 模型或消息平台才能完成。
- R-009: 没有获批权限的主体不能读取或修改客户、联系人或跟进记录。
- R-010: 普通内部视图只展示完成当前工作所需的最少信息；敏感字段必须脱敏、
  隐藏或按已批准规则聚合。
- R-011: 普通内部视图中的业务进度只显示精简摘要，不显示完整阶段细节、原始
  分析或全部进度字段。
- R-012: 未经批准的主体不能通过导出、搜索、接口或其他替代路径绕过脱敏和
  精简进度规则。
- R-013: 记录负责人只能查看完成本人负责记录工作所必需的未脱敏联系方式和
  详细跟进，不能因此查看其他记录或无关敏感字段。
- R-014: 其他已授权业务人员只能查看脱敏后的客户/联系人信息和精简进度。
- R-015: （由 `DEC-0149` 覆盖，见 R-037）管理员全局完整可见；不再强制例外
  访问理由。
- R-016: 联系方式原则上应采集，微信可作为联系渠道；当没有可留存的联系方式
  时，仍允许保存联系人，但必须明确记录这一事实，不能填入猜测值。
- R-017: 销售人员编辑跟进记录时，AI 可以在当前编辑会话中以实时教练方式分析
  草稿，指出可能遗漏、含糊、自相矛盾或需要进一步确认的内容；响应时间目标在
  实现授权前另行确定。
- R-018: AI 建议必须与销售人员输入的事实明确区分，并以问题或建议呈现；未经
  销售人员确认，不得写入正式跟进记录。
- R-019: AI 不得补造客户表述、联系人信息、承诺、业务进度、下一步行动或其他
  未由销售人员提供或确认的事实。
- R-020: AI 不可用、超时或输出无效时，销售人员仍可使用人工流程保存事实记录；
  系统必须明确说明 AI 检查未完成。
- R-021: AI 只能接收当前用户权限允许且完成教练任务所必需的最少上下文；未
  批准外部模型或数据传输前，不得发送真实业务数据到外部服务。
- R-022: AI 教练按适用性检查七个维度（客观事件与参与者；客户明确需求；决策
  参与者及未知项；异议/限制/风险；双方承诺；适用时的下一步/负责人/目标时间；
  待核实事实或证据）。
- R-023: 某维度可以是未涉及、不适用或尚不清楚；AI 不得诱导编造，不得用清单
  生成销售评分或真实性结论。
- R-024: 每轮教练最多展示三个最高价值提问/建议并按重要性排序。
- R-025: 客户建档只强制要求名称、客户类型、信息来源说明和负责人；类别、地区、
  证据引用可暂缺并明确保留为空。
- R-026: 联系人必须从属于一个客户，并至少有真实姓名或可识别的角色称呼；没有
  联系方式时保存联系方式状态，不创建虚假占位值。
- R-027: 每次跟进至少保存发生时间、沟通方式和事实正文；记录者、记录时间、稳定
  身份及归属关系由系统生成。七维教练信息按适用性选填。
- R-028: 下一步行动不是必填项；一旦填写行动内容，必须同时明确负责人，目标时间
  允许未知。系统不得把 AI 建议自动变成下一步行动。
- R-029: 普通协作视图的精简进度只包括最近跟进日期、沟通方式大类、经销售人员
  确认的共享摘要，以及是否已有下一步和目标日期；不包含联系方式、客户原话、
  原始跟进正文、证据附件或 AI 建议。
- R-030: 页面、搜索、导出和 API 必须执行同一字段级可见规则；缺少显示规则时
  默认隐藏。
- R-031: 事实更正必须生成带更正人、更正时间和原因的新版，旧版保留且不能被
  无痕覆盖。第一版不提供业务记录硬删除，只允许归档，错误跟进可撤回但保留审计
  历史。
- R-032: AI 教练在有效草稿发生实质变化并短暂停顿后运行，也允许手动重试；不得
  按每次按键调用，运行/失败/跳过均不阻塞保存。
- R-033: AI 原始提示、问题和未采纳建议只存在于当前编辑会话，不作为业务记录
  长期保存；系统只保留检查是否完成、检查时间，以及被确认后进入正式字段的内容
  归因。
- R-034: AI 实现保持提供方无关；真实业务数据不得发送给外部模型（除非另有获批
  外发路线）。没有获批可用模型时明确降级为人工流程。
- R-035: 发现疑似重复客户或联系人时，系统提示可能重复并展示用户有权查看的最少
  比对信息；用户明确确认后可继续创建，系统不得擅自合并或覆盖。
- R-036: 记录负责人可以维护本人负责客户的当前信息、追加跟进并按 R-031 更正或
  撤回；其他业务人员只读；管理员可无理由修改但自动留痕（覆盖 0.7.0 的「管理员
  例外访问+理由」），仍可归档。

### 新增规则：客户类型（DEC-0149）

- R-037: 每条客户记录有一个必填的**客户类型**字段，三值纯标签：`直接采购`
  （集采/招投标/做项目）、`个人`（团购/电商/一件代发/带货）、`渠道`（代理/
  经销商）。类型不改变任何行为，只用于分类、筛选与统计；同一套建档/跟进/
  公池/商机/脱敏规则适用于所有类型。
- R-038: `个人` 类型第一版仅**预留类型值**：不落地个人建档/跟进/商机流程，
  不接受个人隐私数据（PII）；后续启用须单独 SPEC。
- R-039: `渠道` 类型是纯标签：不做「渠道 → 其客户」层级，不做佣金/结算。
- R-039a: 客户类型建档后可修改，必须留痕（谁改、何时、从什么改成什么）
  （`DEC-0152`）。

### 新增规则：公池（无主状态，DEC-0149）

- R-040: 客户可处于**在池**（无主）状态：进入公池后 `owner` 为空，并带显式
  「在池」状态标记。
- R-041: **进池**是 admin 的手动动作，视同责任转移：写负责人历史（原负责人
  → 无/进池）+ 必填原因（可下拉选）。
- R-042: 池中客户对**全体业务角色脱敏可见**（名称/类型/地区/最近跟进摘要），
  联系方式与原文不放开。
- R-043: **认领**：business_user 可认领公池客户，认领即成为该记录的负责人
  （获得负责人完整详情），认领留审计。第一版不设防囤积护栏。
- R-044: admin 不参与认领，用点名分配（见 SPEC-0002）实现直接流转。
- R-045: 无主客户（owner 为空）的脱敏投影必须单独定义可见性：`owner_user_id
  == user.id` 对无主客户恒为假，投影层必须让「在池」客户以脱敏摘要对业务角色
  可见，不得拒绝所有人、也不得对所有人放开完整详情。

## 7. Data and integrations

### Data concepts

- **客户**：第一版的主记录，代表一个被持续识别和跟进的交易/合作对象；带
  必填「客户类型」。
- **客户类型**：三值纯标签（直接采购 / 个人 / 渠道），不改变行为。
- **联系人**：从属于一条客户记录的自然人联系对象。
- **联系渠道**：可实际使用并允许留存的电话、邮箱、微信标识或其他渠道。
- **跟进活动**：与某一客户明确关联、可按时间回看的一次事实记录。
- **公池**：无负责人客户的集合状态；进池/认领均留审计与负责人历史。
- **责任与来源**：系统保留谁记录、信息从哪里来、谁负责后续处理，以及负责人
  变化历史。

### Minimum data contract

| 对象 | 必需业务信息 | 可选业务信息 | 系统维护信息 |
|---|---|---|---|
| 客户 | 名称、**客户类型**、来源说明、负责人（可为空=在池） | 类别、地区、来源证据引用 | 稳定身份、创建/更新时间、归档状态、负责人变更历史、在池状态 |
| 联系人 | 所属客户；姓名或角色称呼至少一个；联系方式状态 | 职务/角色、电话、邮箱、微信或其他渠道、渠道备注 | 稳定身份、创建/更新时间、录入者 |
| 跟进活动 | 发生时间、沟通方式、事实正文 | 参与者、客户需求、决策参与者、异议/限制、双方承诺、下一步、待核实事项、证据引用、共享摘要 | 稳定身份、所属客户、记录者、记录时间、版本、更正/撤回历史、AI 检查元数据 |

字段规则：

- `来源说明` 可以是销售人员直接获知、公开信息、转介绍或其他真实来源的简短说明。
- `客户类型` 为必填三值枚举，缺省时拒绝保存（R-037）。
- `联系方式状态` 至少区分已有可留存渠道、尚未获得、对方未提供/不可留存；只有
  第一种状态允许出现渠道值。
- `事实正文` 记录销售人员确认的事实，不把模型生成内容标记为客户事实。
- `共享摘要` 是销售人员确认可供其他业务人员查看的简短事实摘要；未填写时，其他
  业务人员只看到日期、沟通方式和不含正文的下一步状态。
- 下一步包含行动内容和负责人，目标日期可以为空；只有目标日期没有行动内容不
  构成有效下一步。

| 更正、撤回、进池/认领和访问审计 | 本人负责记录的业务变更历史 | 不可见 | 完整可见 | 不可见 | 不可见 | 不可见 |

公池客户（owner 为空）：全体业务角色按「其他业务人员/管理层」级别的脱敏摘要
可见（名称/类型/地区/最近跟进摘要）；渠道值与原文不放开（R-042/R-045）。

姓名脱敏不规定固定星号算法；实现任务必须选择对短姓名和少数民族姓名均不会意外
暴露完整身份的确定性规则，并用测试覆盖。

### Integrations

人工核心记录路径不连接也不依赖外部系统。AI 教练使用本地模型还是外部提供方仍
未决定；在模型、权限和数据外传边界获批前，不得向外部服务发送真实业务数据。
外部线索采集属于 SPEC-0003 商机发现，不在本 SPEC。后续集成必须消费已经获批且
验证过的记录/历史接口。

## 8. Failure and edge behavior

- 缺少获批必填信息（含客户类型）时，保存失败并用非技术语言指出缺失内容。
- 同一次提交因重试重复到达时，不应静默产生两条相同记录或活动。
- 无权限访问时，系统拒绝读取或修改，且不泄露记录内容。
- 脱敏规则或精简摘要生成失败时，系统宁可隐藏该内容，也不得回退为完整原始展示。
- AI 教练不可用、超时或输出不符合结构时，系统保留销售人员原始输入并允许人工
  保存，同时明确标记 AI 检查未完成。
- 保存失败时，界面不得显示"已成功"，也不得把未保存内容伪装成历史事实。
- 疑似重复时提示并要求明确确认，不自动合并，不向用户泄露其无权查看字段。
- 进池/认领在并发下（两人同时认领同一客户）时，后到者失败且提示该客户已被
  认领，不得产生双负责人。
- 认领的客户在操作过程中被 admin 进池或转交时，写入前再次校验归属，失败
  则拒绝并提示归属已变化。

## 9. Acceptance criteria

0.7.0 的 AC-001…AC-029 保留（术语「机构/企业」按「客户」理解）。新增：

- AC-030: Given 建档时未选择客户类型，when 保存，then 拒绝并提示必填；类型
  为三值之一时保存成功且可重新打开。
- AC-031: Given 一条 `个人` 类型客户，when 第一版操作，then 仅作为标签保存与
  筛选，不触发个人建档/跟进/商机流程，不接受 PII 录入。
- AC-032: Given 一条 `渠道` 类型客户，when 建档/跟进，then 行为与其他类型一致，
  无层级与佣金逻辑。
- AC-033: Given admin 把一条有主客户进池，when 执行，then owner 置空、在池
  状态置位、负责人历史记录「原负责人 → 进池」且原因必填。
- AC-034: Given 一条在池客户，when 业务人员查看，then 只看到脱敏摘要（名称/
  类型/地区/最近跟进摘要），无渠道值、无原文。
- AC-035: Given 一名 business_user 认领在池客户，when 认领成功，then 成为该
  客户负责人、获得完整详情、认领留审计；再认领已认领客户则失败且不产生双
  负责人。
- AC-036: Given admin 尝试认领，when 请求，then 被拒绝（走点名分配而非认领）。
- AC-037: Given admin 修改任意业务记录，when 执行，then 修改成功且自动留痕
  （谁、何时、改哪条），不强制填写理由。
- AC-038: Given admin 查看全局客户（脱敏摘要），when 展示，then 全部脱敏
  （无渠道值/原文/原话），只读不可改。
- AC-039: Given 一条客户修改其客户类型，when 执行，then 类型更新成功且留痕
  （谁改、何时、从什么改成什么）。

自动化检查与人工业务/视觉验收必须分别记录；一类通过不代表另一类通过。

## 10. Constraints and safety

- 实现必须遵守 `AGENTS.md` 第 5 节全部实现门槛。
- 第一实现路径应可在本地使用非真实数据重复验证，并可在不迁移生产数据的情况
  下撤销。
- [UNKNOWN] 真实数据是否包含个人信息、健康信息、政府项目资料或其他受限信息；
  因此本 SPEC 只允许合成数据验证，不授权真实数据使用。
- 在这些边界确认前，不使用真实业务数据，不部署共享环境，不连接付费或有外部
  副作用的服务。
