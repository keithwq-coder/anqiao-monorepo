# SPEC review checklist

- [ ] The problem is understandable without programming knowledge.
- [ ] Verified facts, inferences, proposals, and unknowns are separated.
- [ ] Goals and non-goals bound the scope.
- [ ] Every business rule has an id.
- [ ] Permissions, data, integrations, failures, and external side effects are
      addressed or explicitly not applicable with evidence.
- [ ] Acceptance criteria are observable and do not claim unrun tests.
- [ ] No legacy statement is treated as current truth without revalidation.
- [ ] No unresolved choice changes required behavior or acceptance.
- [ ] Technical constraints are evidence-based, not model preference.
- [ ] Risks, costs, and irreversible choices are explained in plain language.
- [ ] The requested approval names the exact SPEC id and version.
- [ ] Implementation authorization is requested separately or explicitly
      combined with the approval question.
