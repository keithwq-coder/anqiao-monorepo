## 1. 已确认的纠正

- [VERIFIED] 产品负责人说明，关于经销商、集团分公司和异地关联机构的
  例子用于打开 AI 对“商机”的理解，不是要求系统立即采用某一种固定商机
  类型、推导规则或记录结构。
- [VERIFIED] 产品负责人同意：商机发现不能预先局限为“某个已知客户明确
  提出的一笔采购需求”，也不能因为一个启发性例子就立即收敛到建档、阶段、
  评分或自动化方案。证据：`DEC-0015`。
- [VERIFIED] `SPEC-0001` 已批准机构、联系人和跟进事实；`SPEC-0002` 已批准
  内部身份、角色、责任归属和管理查看边界。两者均未定义广义商机含义。
- [VERIFIED] 旧版 11 阶段漏斗、MEDDIC、评级、金额阈值和预测规则仍是
  `UNTRUSTED LEGACY`，不能用于填充当前商机规则。

## 2. 当前开放理解

[PROPOSAL] 在进入正式 SPEC 之前，先把商机理解为一种“尚未兑现的商业
可能性”，而不是预设为某一种数据库记录、销售阶段或订单。

[PROPOSAL] 商业可能性可能通过需求、关系、资源、场景、区域、项目、渠道、
案例、政策、能力和时机的不同组合而出现。它可能已经对应一个明确目标，也
可能仍表现为一个区域、集团、场景、合作路径或可复制空间。

[UNKNOWN] 上述开放理解最终应如何变成可管理的产品行为。当前不确定它会
形成单一商机记录、多种商机形态、关联网络、机会集合，还是这些方式的组合。

## 3. 商业可能性的产生机制

以下内容全部是 `[PROPOSAL]`，用于扩大探索范围，不是固定分类，也不是
完整清单：

| 产生机制 | 启发性表现 | 不能直接推断的事实 |
|---|---|---|
| 明确需求 | 某机构直接提出采购、项目或合作需求 | 不自动证明预算、决策权或成交概率 |
| 机构关系扩展 | 集团、分支、关联机构或连锁体系中的复制空间 | 不自动证明其他机构存在相同需求 |
| 渠道网络扩展 | 经销商、代理商、集成商或资源伙伴已有客户网络 | 不自动证明伙伴愿意投入或拥有授权 |
| 已有案例复制 | 已成交或已部署场景向其他机构、地区或行业迁移 | 不自动证明新场景条件相同 |
| 产品与场景邻接 | 已有产品、客户问题或实施能力可组合出相邻方案 | 不自动证明客户接受组合方案 |
| 项目生态组合 | 设备、软件、关系、资金或实施能力形成联合入口 | 不自动证明各参与方已同意合作 |
| 区域或行业窗口 | 一个地区、行业或公共项目出现集中需求可能 | 不自动证明具体采购主体或时间 |
| 人员与关系迁移 | 联系人、决策者或合作伙伴进入新的机构或角色 | 不自动转移原机构的权限或业务事实 |
| 集团级扩展 | 一个分支案例可能形成总部、集采或多地区推广空间 | 不自动把分支成交升级为集团成交 |
| 存量关系再激活 | 历史联系、搁置项目或未成交需求因条件变化重新出现价值 | 不自动修改原有关闭结论 |
| 多个弱信号组合 | 单独不足以行动的信息组合后形成值得研究的方向 | 不得把相关性表示成客户已确认事实 |
| 新合作方式 | 资源、产品、渠道或交付能力形成新的进入路径 | 不自动批准结算、佣金或外部承诺 |

该表的目的不是给商机贴标签，而是防止后续 SPEC 只围绕传统直接销售漏斗
展开。

## 4. 商机可能具有的不同形态

以下形态可能重叠，目前不决定是否需要分别建模：

- [PROPOSAL] **具体目标型**：已经可以指向某个机构、项目或采购事项。
- [PROPOSAL] **范围型**：表现为某个集团、地区、行业或场景中的机会空间。
- [PROPOSAL] **路径型**：价值主要来自经销商、集成商、介绍人或其他进入
  路径。
- [PROPOSAL] **组合型**：只有多个参与方、产品或能力组合后才成立。
- [PROPOSAL] **扩展型**：从已有客户、案例、产品或部署关系向外延伸。
- [PROPOSAL] **时机型**：由政策、预算、项目窗口、组织变化或其他条件变化
  触发。

[UNKNOWN] 一个范围型或路径型机会何时需要拆分成若干可执行的具体机会。

## 5. 必须保持的概念分离

后续收敛时至少要避免以下混淆：

1. **事实与可能性**：已经发生或被确认的事实，不等于从事实推导出的商业
   可能性。
2. **启发与规则**：一个例子可以打开思路，但不能自动变成固定产品分类。
3. **发现与管理**：发现可能性、决定是否投入、推进销售以及关闭结果是不同
   问题。
4. **目标与路径**：最终使用者、采购方、付款方、决策方、经销商、集成商和
   介绍人可能不是同一主体。
5. **来源与结果**：商机从哪里被发现，不等于最终通过哪条路径成交。
6. **机会空间与具体事项**：一个集团或区域的扩展空间，不一定等于一笔可以
   直接关闭的交易。
7. **业务价值与漏斗状态**：值得研究的商业可能性不必已经进入传统销售
   阶段。

## 6. 对产品负责人例子的正确使用

经销商向集团某分公司供货，同时 CRM 已知同集团另一地区存在关联机构，这个
例子应当用来证明：孤立信息之间的连接可能揭示新的商业可能性。

它当前不证明以下内容：

- 所有集团关联机构都应自动成为商机；
- 集团关系必须成为一种固定商机类型；
- 目标机构已经存在需求、预算或采购意向；
- 应当自动创建记录、自动评分或自动进入预测；
- 一个集团只能有一条或必须有多条商机；
- 经销商一定是新机会的唯一或最佳进入路径。

## 7. 对 SPEC-0003 的影响

`SPEC-0003` 不应从阶段数量、赢单概率、金额字段或传统漏斗模板开始。正式
起草前需要依次澄清：

1. CRM 是否只管理已经被人识别的商机，还是也承担帮助发现新商机的产品
   责任；
2. 广义商业可能性在什么情况下需要成为可持续跟进的对象；
3. 具体目标、范围、进入路径和多个参与主体之间如何保持业务含义；
4. 已确认事实、人的判断和 AI/规则推导如何清楚区分；
5. 一个广义机会如何拆分、合并、关联、推进、搁置或关闭；
6. 权限、脱敏、责任归属和审计如何继承 `SPEC-0001` 与 `SPEC-0002`；
7. 哪些内容属于后续线索采集、匹配评分、提醒和报表 SPEC，而不是在本 SPEC
   中提前决定。

## 8. 当前明确不决定

- 商机必须或不必须具有明确目标机构；
- 商机类别、阶段数量、阶段名称和转换条件；
- 系统自动发现、自动创建或人工确认的具体方式；
- 集团级机会和分支机构机会的结构关系；
- 金额、概率、评分、评级、预测或优先级公式；
- 赢单、丢单、搁置、无效和重复的最终原因清单；
- 负责人冲突、渠道保护、区域保护、佣金或结算规则；
- 外部数据源、模型提供方和真实数据传输。

## 9. 下一发现门禁

[VERIFIED] `DEC-0016` 确认：CRM 必须主动连接批准范围内的已有信息，向业务
人员揭示原本可能没有注意到的商业可能性，并同时呈现支持依据；人负责最终
业务判断。系统发现不能冒充客户意向、已确认需求、承诺或预测。

[VERIFIED] `DEC-0017` 确认：系统揭示的商业可能性必须与人已明确决定投入
经营的业务工作保持为两个不同的逻辑层次，不能合并成仅靠状态标记区分的
同一种记录。

[VERIFIED] `DEC-0018` 确认：现阶段系统发现结果以“提醒”方式呈现（连同
依据），不设正式认领/升级机制；人被提醒后通过既有 `SPEC-0001` 跟进记录
正常处理。因此“进入人经营层最低需要何种承诺”在当前阶段的答案是：无需
专门动作。

## 10. 主动发现的产品责任边界

由 `DEC-0016` 确认：

- CRM 不是被动登记簿；它承担帮助人看见新商业可能性的责任。
- 每个系统揭示结果必须能够说明使用了哪些获准信息、形成了什么推理，以及
  哪些关键事实仍不确定。
- 人决定是否投入、如何验证和怎样推进；系统不能把“被发现”表示为“已被
  客户确认”。
- 主动发现必须继承 `SPEC-0001` 和 `SPEC-0002` 的最小必要、脱敏、权限与
  审计边界。
- 本决定不预先选择 AI、固定规则、关系图谱、评分模型或外部数据源。

## 11. 发现结果到业务工作的候选边界

[VERIFIED] `DEC-0017` 确认后续 SPEC 必须区分以下两个逻辑层次（仍不决定
具体页面或数据结构）：

1. **系统揭示的商业可能性**：允许目标、路径或价值仍不完整；必须保留依据、
   推理、不确定项和发现时间；不能进入业绩预测，也不能表示为客户确认事实。
2. **人决定投入的持续业务工作**：有人愿意承担验证或推进责任，后续活动和
   结果需要持续保留；是否称为“正式商机”仍待确认。

[PROPOSAL] 人可以采用、暂缓、忽略、合并或要求补充依据，但系统不得因为
未采用就篡改原始事实，也不得把一次忽略永久等同于该方向没有价值。

[VERIFIED] 两个层次必须明确分离，由 `DEC-0017` 确认。

[VERIFIED] `DEC-0018` 确认：现阶段两层之间不设关卡——发现层以“提醒”呈现，
人经营层沿用既有 `SPEC-0001` 跟进记录，无需专门的认领/升级动作。是否需要
一个独立的“商机对象”仍未决定，只有在后续确有需要时再定。

[VERIFIED] `DEC-0019` 确认：发现功能可跨负责人连接全公司获准范围内的数据
来识别机会，但推送给接收者的提醒（含理由）必须遵守 `SPEC-0001` 脱敏与精简
进度规则，且颗粒度不得成为反推受保护信息的通道；获取受保护细节仍走原有
负责人/管理员例外流程。

[VERIFIED] `DEC-0020` 确认：提醒发给相关记录的负责人，各自收到本方的脱敏
提醒、在本人地盘内行动；不新增主管/协调人分派角色，也不自动挑“最合适的
一个人”。

[VERIFIED] `DEC-0021` 已解决上述边界：多负责人协同不在本阶段（非目标）、
无负责人的记录发给主管、无人处理的提醒即未读消息、管理层暂不提供发现汇总
视图。发现探索的结论已落入 `SPEC-0003 v0.2.0`，现处于 `20-review`。
